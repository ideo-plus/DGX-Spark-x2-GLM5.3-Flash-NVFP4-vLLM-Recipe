# ACPI 熱区域 0・4 の熱源の切り分け (#11 段階 1)

日付は 2026-09-23 JST。
[full 構成の計測](2026-09-23-full-context.md) では、cold 128k prefill の間に head の ACPI 熱区域 0・4 が 89.8℃ に達した。
このときの熱源を、設定を変えずに切り分けた。
記録には、[PR #13](https://github.com/ideo-plus/DGX-Spark-GLM5.3-Flash-Recipe/pull/13) で広げた `serve watch` を使った。
実機操作は対話側が行った。

## 条件

- 構成は `p2-nope-tp2-full`（文脈長 163840、同時実行 16）。
- GPU クロックの上限 `-lgc 300,1800` は、両台に入れ直してから始めた。
- 全 16 関門、ready、今回分の IB（各台で初期化 1 回、経路確定行 256 行がすべて IB）、`serve smoke --max-tokens 512` を確認した。
- 負荷は `bench run --suite prefill --profile quick --set prefill.trials=10`。
  19:57〜20:20 JST に実行し、状態 `completed`、失敗 0 だった。
  cold 128k は 10 試行で、最初のトークンまでの中央値は 83.9 秒、prefill は 1,539 tok/s（変動係数 0.002）。
  熱源の切り分けのための計測なので、要約は公開しない。
- `serve watch --interval 10s` で、熱区域 7 つ、hwmon、GPU、コアごとの CPU を記録した（139 観察）。
  - hwmon の内訳は、`hwmon0` が acpitz、`hwmon1` が NVMe、`hwmon2`〜`5` が ConnectX-7（mlx5）。
  - 熱区域と hwmon を見つけるのに、起動から約 2 分半かかった。
- 安全のため、どれかの熱区域が 92℃ に達したら bench を中断する一時の見張りを並べた。これは作動しなかった。

## 結果

| 項目（head / worker） | 最高 |
|---|---|
| 熱区域 0 | 86.9 / 79.7 ℃ |
| 熱区域 4 | 86.9 / 76.1 ℃ |
| 熱区域 1・3・5・6 | 66〜68 / 65〜68 ℃ |
| GPU 温度 | 64 / 63 ℃ |
| GPU 電力 | 28.5 / 28.7 W |
| ConnectX-7（mlx5 asic） | 67 / 67 ℃ |
| NVMe | 57 / 58 ℃ |
| SM クロック | 1768〜1774 / 1774〜1781 MHz |

90℃ 以上になった観察はなく、`thermal` の出来事も起きなかった。

## 切り分け

どの温度も負荷と一緒に上がるので、生の値どうしの相関（0.6〜0.95）では熱源を区別できない。
そこで、熱区域 1 との差（熱区域 0 だけが余分に熱い分）を指標にした。熱区域 1 は GPU 温度とよく揃う（相関 0.97〜0.98）。

| 指標との相関（熱区域 0 − 熱区域 1） | head | worker |
|---|---:|---:|
| 最も使われたコアの使用率 | 0.50 | 0.81 |
| GPU 電力 | 0.49 | 0.85 |
| ConnectX-7 の温度 | **0.08** | 0.63 |

- **余分な熱の大きさ:** 待機中は約 1℃ だった。推論サーバーが処理している間は、条件によらず平均 10〜16℃ になった。
  cold 128k だけが特別に高いわけではない。head の最大 +22.9℃ は cold 8k と 32k のときだった。
- **ConnectX-7 は熱源ではない:** 両台で同じ 67℃ なのに、熱区域 0 は head が 7℃ 高い。
  head では、余分な熱との相関もほぼ 0 だった。
- **CPU との関係:** 処理中は両台とも、X925（コア 5〜9、15〜19）のうち 2 つがほぼ常に 100% だった。
  張り付くコアは入れ替わる。熱区域 0・4 の余分な熱は、この張り付きと一緒に現れて一緒に消える。
- **GPU との関係:** GPU は、熱区域 1 など全体の底上げに効いている。
  GPU の電力は上限 1800 のもとで 30 W 未満に収まっていて、余分な熱の説明にはならない。

**判断:**
熱区域 0・4 の余分な熱は、処理中に X925 の 2 コアが張り付くことと結び付いている可能性が高い。
推論サーバーの worker と EngineCore の常時の待ち受け（busy-poll）と推定する。
ConnectX-7 と NVMe は除外できる。
head が worker より高い理由として、次の 2 つが考えられる。

- head は API サーバー（トークナイズなど）も動かしている
- head には別の常駐コンテナがある

ただし、どちらも確かめていない。
熱区域の名前がすべて `acpitz` なので、区域 0・4 が CPU のクラスタの温度だと断定はできない。

## 次にすること（段階 2 の案）

- X925 の周波数に上限をかけ（例: 3.0 GHz）、同じ負荷で熱区域 0・4 と prefill・decode の速さを比べる。
  - `cpupower frequency-set` か sysfs への書き込みが要り、root の権限が必要である。
  - 両台の sudoers に、`cpupower frequency-set -u *` と `frequency-set -u 3900MHz`（戻す）だけを許す設定を足してもらう必要がある。
- あわせて、vLLM の待ち受けを抑える設定があるかを調べる。これは TAKT での調査。
