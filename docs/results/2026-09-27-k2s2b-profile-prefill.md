# K2 第 2b 段の重み（`k2s2b`）での 1 ステップの内訳と prefill

日付は 2026-09-27 JST。[第 2b 段の記録](2026-09-27-k2-stage2b.md)の「次に確かめること」の 2 に当たる。
`k2s2b` の重みと重ね合わせ `k2s2b` で、MTP の N = 3 の構成を 2 回起動し、次の 2 つを測った。

- **A. 1 ステップの GPU の時間の内訳。** [手順](../vllm-baseline/k2-profile-procedure.md)に沿って、torch プロファイラーを付けた構成で測った。[元の重みの内訳（N = 3）](2026-09-26-k2-profile-mtp3.md)と比べる。
- **B. 入力の処理（prefill）。** 成功の基準の「32k トークンの入力の処理」を、今の構成で測り直した。

2 つの上限（GPU 1800 MHz、X925 3.0 GHz）は、どちらの回も両台で効いていた。実機操作は対話側が行った。

## 要約

- **1 ステップは 137.7 ms から 95.1 ms に縮んだ（−31%）。** プロファイラーの窓の長さ ÷ ステップ数の値。
  - 重みの GEMV・GEMM（BF16 と FP8 の合計）は 63.0 ms から 32.9 ms になった。K2 で FP8 にした層が、読む量のとおりに縮んだ。
  - カーネルのない隙間は 15.7 ms から 4.8 ms になった。
- **いちばん大きいのは MoE の専門家の GEMM で、1 ステップ 40.4 ms（42%）。** 元の重みの 42.5 ms とほぼ同じで、K2 では減らない。
- **FP8 の線形層（`humming` のカーネル）は、1 ステップ 26.2 ms（28%）。** 集計の道具は、この系統をまだ「その他」に入れる。下の表は、その分を分けて数え直したもの。
- **下書きの側の BF16 の大きな GEMV（元は 1 ステップ 14.1 ms）は 1.9 ms になった。** 代わりに、語彙（154,880）の半分に近い幅の FP8 の GEMM（77568 × 4096）が、1 ステップ 4.2 回・5.4 ms 現れた。下書きと検証が、FP8 にした lm_head を使うようになったと見る（推測）。
- **32k の cold prefill は 1,386 tok/s で、成功の基準（2,000 tok/s 以上）に届かない。** 2026-09-23（元の重み、投機なし、上限なし）の 1,525 tok/s より 9% 遅い。
- **warm 8k は、プレフィックスキャッシュに当たらなかった**（当たった割合 0.000）。最初のトークンまでの時間は cold とほぼ同じ 5.5 秒だった。warm 32k・128k も、2026-09-23 より遅い（1.25 → 3.64 秒、2.16 → 3.79 秒）。
  - 原因は vLLM の設計による。MTP を使うと、キャッシュに当たった最後のブロック（この構成では 4608 トークン）を捨てて計算し直す（下の「warm がキャッシュに当たらない理由」）。
- trace に、要求と応答の本文は入っていなかった（下の「本文の確認」）。

### warm がキャッシュに当たらない理由

vLLM `0961bbae` のソースを読んだ結果と、過去の計測ランを突き合わせた。

- **MTP を使うと、キャッシュに当たった最後のブロックを捨てる。** `vllm/v1/core/kv_cache_coordinator.py` は、EAGLE と MTP の場合に「最後に当たったブロックを計算し直す」と定めている。下書きのヘッドが要る隠れ状態を得るためと、複数のモジュールの MTP で先読みしたトークンがキャッシュを汚さないようにするためである。捨てる単位は、スケジューラーのブロックの大きさである。
- **この構成のブロックは 4608 トークンである。** 起動のログは、MTP 付きで 4608、投機なしで 4352 だった（KDA の状態のページの大きさにそろえるため）。
- **過去の計測ランの当たった割合と合う。**

| 構成 | ブロック | warm 8k | warm 32k |
|---|---:|---:|---:|
| 投機なし（2026-09-23、3 回） | 4352 | 0.445〜0.485 | 0.784〜0.855 |
| MTP の N = 3（今回） | 4608 | 0.000 | 0.712 |

  - warm 32k の 0.712 は、4608 トークンのブロック 5 つ分（23,040 ÷ 32,376）に当たる。投機なしなら当たるはずの 6 つ目が捨てられた。
  - warm 8k は、当たるブロックがもともと 1 つしかなく、それが捨てられて 0 になった。
- **影響。** MTP を使う限り、要求ごとに少なくとも 4608 トークンを計算し直す。今の prefill の速さ（約 1,400 tok/s）では、最初のトークンまでが約 3.3 秒延びる。takt は同じ前置きを何度も送るので、PLAN.md の P4（プレフィックスキャッシュが長い会話で効き続けるか）に効く。
- **減らす手がかり。** `vllm/v1/core/single_type_kv_cache_manager.py` は、ハッシュの単位がブロックより細かいときは、捨てるのをハッシュの 1 単位だけにする。この構成で細かい単位を使えるかは、確かめていない。

## 見積もり（次の手を選ぶため）

どれも、この内訳からの見積もりで、測った値ではない。

- **FP8 の線形層を NVFP4 にする。** 読む量が半分になれば、26.2 ms が 13 ms 前後になり、1 ステップは約 14% 縮む。第 2b 段の確認の段（37.8 tok/s）に当てはめると 44 tok/s 前後で、60 tok/s には届かない。品質の確認（KDA の射影を 4 bit にした公表値がない）が要る。
- **MoE の専門家の GEMM（40.4 ms）は、K2 では減らない。** 投機の検証で読む専門家が増えるため、元の重みの内訳では、N = 3 で投機なしの約 2.8 倍だった。受理長を伸ばす K3（深いドラフター）は、この項も増やしうる。
- **60 tok/s（コード・英語）には、受理長 3.1 のままなら 1 ステップ約 52 ms が要る。** 上の 2 つのどちらか 1 つだけでは届かない見込み。

## 次に確かめること

1. MTP で捨てるキャッシュの量を減らせるか（P4）。ハッシュの単位を細かくする設定がこの版と KDA の構成で使えるかを、ソースで確かめる。
2. head の重みの読み込みが worker の約 3.3 倍かかる原因（#37）。
3. 集計の道具（`experiments/k2-profile/summarize_trace.py`）の区分に、FP8 の線形層（`humming`）を足す。
4. 次の手（FP8 の線形層の NVFP4 化か、K3 か）を、上の見積もりと品質の見込みで決める。
