# 上限を常設した状態での agent 20k の初回計測

日付は 2026-09-24 JST。
[spark-power-caps](../../ops/spark-power-caps/README.md) で、GPU の上限 1800 と X925 の上限 3.0 GHz を両台に常設した後の、最初の計測である。
[prefill・並列・長文脈の計測手順](../vllm-baseline/full-context-procedure.md) §5 の、任意の agent ランを最短の段階で行った。
実機操作は対話側が行った。

## 条件

- 構成は `p2-nope-tp2-full`（文脈長 163840、同時実行 16）。
- 起動前に、両台で `spark-power-caps.service` が `active`、X925 の `scaling_max_freq` が 3,000,000 kHz であることを確かめた。
- 全 16 関門、ready、今回分の IB（各台で初期化 1 回、経路確定行 256 行がすべて IB）、`serve smoke --max-tokens 512` を確認した。
- `bench run --suite agent --profile quick --set agent.end_tokens=20000` を 08:05〜08:10 JST に実行した。
  20k の 1 段だけで、会話 5 本、50 試行、出力の上限は 256。
- `serve watch --interval 10s` で記録した（32 観察）。

## 結果

要約は [20260923T230512Z-p2-nope-tp2-full-pdsx2i](20260923T230512Z-p2-nope-tp2-full-pdsx2i/summary.md)。状態は `completed`。

| 項目 | 値 |
|---|---|
| 実際の入力（中央値） | 21,094 トークン |
| 正しいツール呼び出し | 50 / 50（崩れ 0） |
| 崩れた割合の 95% 区間 | 0.000〜0.071 |
| プレフィックスキャッシュから読んだ入力（中央値） | 17,408 トークン |
| 最初のトークンまで（中央値 / 最大） | 2.9 秒 / 20.1 秒 |

- 50 試行すべてが `correct` だった。
  ほかの分類（`no_call`、`wrong_call`、`args_unparseable`、`markup_leaked`、`empty_or_truncated`、`request_failed` など）は 0 件。
- **「試行の数が足りない」の印が付いた。**
  崩れのしきい値 0.01 を下回ると言うには、崩れ 0 件のままで 299 試行が要る。この結果は「20k で崩れは見られなかった」までであり、1% 未満の保証ではない。
- **「長さが外れた」の印が 30 件付いた。**
  実際の入力が狙いの 20,000 より約 5% 長い。concurrency と同じ種類のずれで、#9 で扱う。
- 同じ会話の中では、前の入力がキャッシュに乗るため、最初のトークンまでの時間は 3 秒前後に収まった。

| 項目（head / worker） | 最高 |

| 熱区域 0・4 | 64.9 / 62.8 ℃ |
| GPU 温度 | 59 / 58 ℃ |
| GPU 電力 | 26.8 / 27.1 W |

- 熱区域は、90℃ まで 25℃ 以上の余裕があった。
  上限なしの [段階 1](2026-09-23-thermal-source.md) の prefill で 86.9℃ だった head の熱区域 0 は、64.9℃ だった。ただし、負荷の種類（agent と prefill）が違うので、同じ条件の比較ではない。
- 上限が効いていたことを、計測の記録（`result.json`）だけで確かめられた。

## 次にすること

- 崩れの割合を判定できるだけの試行数で測る（`--set agent.trials_per_stage=300`）。
  1 段 50 試行が 5 分だったので、20k だけなら 30 分ほどの見込み。
- 40k〜120k の段階を足す。長い段ほど、キャッシュが効かない最初の試行が重くなる。熱は `serve watch` で見ながら進める。
