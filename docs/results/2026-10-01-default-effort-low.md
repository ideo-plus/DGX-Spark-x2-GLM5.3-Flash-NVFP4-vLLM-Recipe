# 既定の思考の深さを low にする (#158、#159)

日付は 2026-10-01 JST。実機操作は対話側が行った。

**結論**:
- 推奨の構成 `glm53-tp2-mtp3-marlin` の既定の思考の深さを `low` にした (PR #160)。
  - 足した引数は `--default-chat-template-kwargs '{"reasoning_effort":"low"}'` である。
  - 要求の側で `reasoning_effort` を送れば、深さは今までどおり変えられる。
- 既定 (最大) のままでは、コードの課題で答えが本文に出ないことが多かった。low では、すべての試行で 1.4 秒以内に答えが出始め、品質も落ちなかった。
- これまでの `bench` の decode の値は、思考の文を書く速さだった。答えの本文を書く速さで測ると、次の 2 つが成功の基準に届いていない。
  - コード・英語は 44.3 tok/s (基準 45)
  - 同時 2 本の 1 本あたりは 23.5 tok/s (基準 30)
- 判定の決まりも、`PLAN.md` §3 に書き足した。生成速度は、答えの本文を生成する速さで判定する。

## 1. 既定 (最大) で答えが返らない (#158 の探り)

`bench` の decode のコード・英語の課題文 (題を変えて 5 種類) を、推奨の構成に送った。

- **送り方**: 温度 0、出力の上限 8,192 トークン。
- **数え方**: 本文が出始めたら打ち切った。

| 経路 | 深さ | 本文に答えが出た | 本文が出始めるまで | 思考 |
|---|---|--:|--:|--:|
| `/v1/chat/completions` | 最大 (当時の既定) | 5 本中 2 本 | 74 秒、155 秒 | 1,968〜8,192 トークン |
| `/v1/chat/completions` | high | 3 本中 3 本 | 1.2〜1.5 秒 | 34〜39 トークン |
| `/v1/chat/completions` | low | 3 本中 3 本 | 0.7〜1.1 秒 | 8〜20 トークン |
| `/v1/messages` | 最大 (当時の既定) | 3 本中 0 本 | — | 3 本とも 8,192 トークン |

- **最大の深さ**:
  - 8 本とも、思考の中にコードの囲み (` ``` `) があった。
  - 答えのコードを思考の中に書いたまま終わるか (`stop`)、上限まで思考を書き続けた。
- **分け方は正常**: 出力の上限を 3,000 トークンにして、ストリームありとなしで送り直した。どちらでも同じだったので、パーサーの分け方の不具合ではない。

## 2. 既定の深さを high・low にした一時構成 (`bench` の `fast`)

一時構成は、推奨の構成にこの引数だけを足したもので、Git の管理の外に置いた (測ったあとに消した)。
`bench` は、要求に深さを付けない。

### decode (中央値 tok/s、各 10 回、かっこの中は受理長)

| 条件 | 最大 (9/30) | high | low |
|---|--:|--:|--:|
| コード・英語 | 45.88 (3.11) | 40.06 (2.69) | 43.56 (2.92) |
| コード・日本語 | 43.94 (2.91) | 41.91 (2.72) | 42.49 (2.74) |
| 散文・英語 | 43.46 (2.92) | 38.20 (2.49) | 37.38 (2.46) |
| 散文・日本語 | 42.83 (2.78) | 39.19 (2.46) | 37.66 (2.35) |
| JSON・英語 | 44.77 (3.04) | 45.60 (3.06) | 48.18 (3.21) |
| JSON・日本語 | 40.10 (2.66) | 47.90 (3.14) | 48.37 (3.18) |
| 思考だけで 256 トークンを使い切った試行 | 59 / 60 | 2 / 60 | 0 / 60 |

- **最大の深さの値**: 思考の文を書く速さである。思考の文は、課題文の言い換えや同じ言い回しが多い。そのため、MTP の下書きが当たりやすい (受理長 3.11)。
- **答えの本文**: コード・散文の答えの本文は、下書きが当たりにくい。そのため、high・low では受理長も速さも下がる。
- **JSON**: 答えの本文のほうが下書きが当たりやすく、速くなった。

### quality (`fast`)

| 項目 | 最大 (9/28) | high | low |
|---|--:|--:|--:|
| toolcall | 7/10 | 8/10 | 10/10 |
| humaneval+ (上限 2,048) | 10/10 | 10/10 | 10/10 |
| needle 8k・32k | 2/2 | 2/2 | 2/2 |

問題の数が少ないので、差は誤差の範囲である。品質が落ちる兆しは見えない。

- **low を選んだ理由**:
  - 答えはすべての試行で出た。
  - 品質は同じか上だった。
  - コードは high より速く、JSON は最大より速い。
- **low の弱いところ**: 散文は、最大より約 12% 遅い。

## 3. コミットした構成の測り直し (PR #160 のあと)

起動の前に、2 台のページキャッシュを捨てた。
クロックの上限は GPU `300〜1800 MHz`、X925 3.0 GHz である。
起動のあと、要求に何も付けずに送ると、思考は「Output numbers 1-200.」の 1 文で終わり、すぐに本文が出た。

### sparkDash (1.8.6、各 1 回)

sparkDash は思考オフを求める。しかし、公式のテンプレートはそれを読まない。
そのため、既定の low で考え、答えの前に短い思考の 1 文が付く。sparkDash は、その 1 文も出力として数える。

| 項目 | 値 |
|---|--:|
| 構造化 同時 1 本 | 60.64 |
| 構造化 同時 2 本 (1 本あたり / 合計) | 49.01 / 97.11 |
| 散文 同時 1 本 | 43.74 |
| 散文 同時 2 本 (1 本あたり / 合計) | 29.02 / 57.03 |
| コード 同時 1 本 | 59.03 |
| コード 同時 2 本 (1 本あたり / 合計) | 41.54 / 80.53 |
| prefill 8k (最初のトークンまで) | 1,428 (5.8 秒) |
| prefill 32k | 1,598 (20.5 秒) |
| prefill 128k | 1,584 (82.8 秒) |

GPU の実クロックの最高は 1,774〜1,781 MHz、2 台とも `NV_ERR_NO_MEMORY` は 0 件。

### 入力の処理 (prefill)

`bench` の cold 32k・128k は、9 月 30 日の値 (1,331・1,332 tok/s) をそのまま使う。
思考の深さの既定は、テンプレートの書き出しを変えるだけで、入力の処理の量は変わらない。
sparkDash の prefill も、9 月 30 日の値と同じ範囲だった。
