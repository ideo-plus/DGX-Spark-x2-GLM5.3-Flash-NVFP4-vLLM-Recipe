# K2 第 2a 段: MLA・KDA のまとめていない射影・lm_head を FP8 にした重み（`k2s2a`）

日付は 2026-09-27 JST。[ADR 0007](../decisions/0007-k2-stage2.md) の第 2a 段である。派生の重み `k2s2a` を作り、vLLM の修正（重ね合わせ `k2s2a`、PR #78）を bind mount で重ねて起動した。探り（`probe`）と確認（`fast`）で、速さと壊れを見た。
2 つの上限（GPU 1800 MHz、X925 3.0 GHz）は、どの回も両台で効いていた。実機操作は対話側が行った。

## 要約

- **確認の段（出力 256 トークン、MTP の N = 3）で、4 条件とも 32〜34 tok/s になった。** 元の重みの同じ確認（[記録](2026-09-25-k1-n-sweep.md)）より 18〜25% 速い。**散文・日本語の 32.1 tok/s は、成功の基準（30 tok/s 以上）を超えた。**
- 探り（出力 128 トークン）では、次のとおり。
  - 投機なし: 元の重みより 22〜29% 速い。code/en は 14.06 → 18.19 tok/s。
  - N = 3: 14〜20% 速い。code/en は 34.0 → 38.9 tok/s。
- 受理長は、ほぼ変わらない（確認の段で 2.85〜3.08、元の重みは 2.79〜3.09）。速くなった分は、1 ステップが短くなったことによる。
- **壊れは見つからなかった。**
  - toolcall は、探りの 5 問・確認の 10 問とも、正解・不正解が投機なしの基準の回と同じだった。
  - needle（8k・32k）は正解。
  - `repetition_loop` と `replacement_char` の印は 0 件。
- humaneval+（確認の段、10 問、上限 2048）は 9/10 だった。落とした HumanEval/9 は、上限 2048 で切れた。元の重みの確認では 1,521 トークンで答え終わり、正解だった。このほかの 9 問は、答え終わって正解した。1 問の差なので、品質の低下とはまだ判断しない。記録の段（`quick` 以上）で確かめる。
- 同時 2 本の 1 本あたりは 21.6 tok/s（元の重み 20.2）で、基準（30 tok/s）には届かない。

## 作った重みと重ね合わせ

| 項目 | 値 |
|---|---|
| 重み | `k2s2a`。道具 `experiments/k2-quant`（commit `a6a9d38`）の `--preset k2s2a` |
| FP8 にした層 | 第 1 段（dense の MLP、共有の専門家）、MLA の射影（`q_a_proj`・`kv_a_proj_with_mqa`・`q_b_proj`・`o_proj`）、KDA の `o_proj`・`g_b_proj`、lm_head。計 251 モジュール |

| 変換 | 2 台それぞれ、約 8.5 分。2 台の道具のマニフェストはバイト単位で一致した。19 ファイル、193,433,037,881 バイト |
| 照合 | `serve verify` で、2 台とも 19 ファイルがマニフェストと合った |
| 重ね合わせ | `k2s2a`（PR #78）。直した 3 ファイル（`vocab_parallel_embedding.py`・`glm5next/common/model.py`・`kda.py`）を、読み取り専用で重ねた。配った写しは、2 台とも Mac の写しと一致した |
| 読み込み | `--load-format auto`（mmap）。重みの読み込みは約 480 秒 |

`GPU KV cache size` は、投機なしで 1,826,641 トークン（元の重み 1,708,119）、N = 3 で 1,039,753 トークンだった。
