# K1: モデル付属の MTP を下書き 1 トークンで有効にした計測（`p2-nope-tp2-mtp1`）

日付は 2026-09-25 JST。
[手順](../vllm-baseline/mtp-procedure.md)に従い、比較の基準の `p2-nope-tp2-full`（投機なし、N = 0）と、`p2-nope-tp2-mtp1`（N = 1）を同じ日に測った。
2 つの上限（GPU 1800 MHz、X925 3.0 GHz）は `spark-power-caps.service` が入れていて、両方の回で効いていた（下の「熱と上限」）。
実機操作は対話側が行った。各 bench には、92℃ の安全停止の見張りを付けた。見張りは一度も働かなかった。

## 要約

- 1 本ずつの decode は **14.0 → 22.9〜23.9 tok/s（1.62〜1.70 倍）**。受理長は 1.79〜1.87。
- 1 ステップの時間は、約 71 ms から約 78 ms へ、約 10% 伸びた。速くなった分は「受理長 ÷ ステップの伸び」（1.87 ÷ 1.10 ≒ 1.70）で説明できる。
- 同時の本数が増えるほど、伸びは小さくなる。合計の tok/s は、2 本で 1.35 倍、4 本で 1.27 倍、8 本で 1.22 倍。
- 出力の壊れの印（`repetition_loop`、`replacement_char`）は、decode・concurrency のどちらにも 0 件。needle は 30/30、toolcall は 37/50 で、正解・不正解の問題は N = 0 と 1 問も変わらなかった。
- humaneval+ は 26/40 から 22/40 に下がった。ただし、どちらの回も、不正解はすべて出力の上限（1024 トークン）で切れたものだった。下がった 4 問も、N = 1 で考えが長くなり、上限で切れたものである（下の「品質」）。
- 手順 §5 の `--set decode.max_tokens=4096` の decode は、N = 0 と N = 1 のどちらも**流していない**。N ≥ 2 の前に必要になる（§7 の #58454 の確認）。

## 構成と KV 容量

- イメージ、重み、TP = 2、文脈長 163,840、同時 16 本は `p2-nope-tp2-full` と同じ。違いは `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'` だけ。
- 起動ログの KV 容量は `GPU KV cache size: 1,034,240 tokens, Maximum concurrency for 163,840 tokens per request: 6.31x`。手順 §4 の進む条件（163,840 トークン以上、1 倍以上）を満たした。`full` の 1,708,119 トークンから、MTP の層の分だけ減っている。

### 1 ステップの時間の出し方

手順 §5 は、2 つの定義が同じ結果になることを確かめてから使うように求めている。今回は**一致しなかった**。

- 「試行の生成時間（最初のトークンから最後のトークンまで）の合計 ÷ `decode_steps`」: N = 0 は 70.8〜71.5 ms、N = 1 は 77.2〜78.4 ms。
- 「`tokens_per_step ÷ decode_tps`」: N = 0 は 82〜91 ms、N = 1 は 91〜99 ms。

原因は `tokens_per_step` の中身にある。`bench` はこれを vLLM の `iteration_tokens_total` の合計 ÷ 回数から出していて、合計には prefill の回の入力トークンも入る。そのため、投機なしでも 1.16〜1.27 になる。出力のトークン数 ÷ `decode_steps` は、N = 0 で 1.000、N = 1 で 1.786〜1.866 になり、受理長と一致する。上の表は 1 つ目の定義を使った。`bench` の側の扱いは issue で直す。

## concurrency（出力 256 トークン、5 回ぶん）

要約は [N = 0](20260925T060946Z-p2-nope-tp2-full-kzx7ho/summary.md)、[N = 1](20260925T071331Z-p2-nope-tp2-mtp1-8r6xk8/summary.md)。値は中央値。

| 水準 | N = 0 の 1 本あたり | N = 1 の 1 本あたり | N = 0 の合計 | N = 1 の合計 | 合計の倍率 |
|---|---:|---:|---:|---:|---:|
| 1 本 | 14.036 | 23.325 | 14.091 | 23.416 | 1.66 |
| 2 本 | 13.264 | 18.259 | 25.151 | 34.049 | 1.35 |
| 4 本 | 9.950 | 12.862 | 37.068 | 47.025 | 1.27 |
| 8 本 | 7.008 | 8.867 | 50.161 | 60.942 | 1.22 |

- 同時の本数が増えると、1 ステップで検証するトークンが増え、1 ステップの時間の伸びが大きくなる。そのため、倍率は小さくなる。それでも、8 本まではどの水準でも N = 1 のほうが速い。
- どちらの回も、印は 0 件（`replacement_char` と `repetition_loop` を含む）。

## 品質（`quality`、`quick`）

要約は [N = 1](20260925T072220Z-p2-nope-tp2-mtp1-4s254r/summary.md)。N = 0 は 2026-09-23 の [記録](2026-09-23-full-context.md)の値（同じイメージ・同じ構成。temperature = 0）。

| 条件 | N = 0 | N = 1 |
|---|---:|---:|
| `quality/toolcall` | 37 / 50 | 37 / 50 |
| `quality/code/humaneval+` | 26 / 40 | 22 / 40 |
| `quality/needle`（8k・32k・128k、各 5 位置 × 2 回） | 30 / 30 | 30 / 30 |

- toolcall は、50 問のどれも、正解・不正解が N = 0 と同じだった。
- humaneval+ は、どちらの回も、不正解はすべて `stop_reason = max_tokens`（N = 0 は 14 問、N = 1 は 18 問）だった。上限で切れずに答えた問題は、すべて正解している。下がった 4 問（HumanEval/19、25、34、38）は、N = 0 では 424〜863 トークンで答え終わっていたが、N = 1 では 1024 トークンで切れた。
- temperature = 0 でも、MTP の検証では計算の形が変わるので、出力は N = 0 と完全には一致しない。考えの長さの揺れが、1024 トークンの上限をまたぐかどうかを変えた、と読むのが自然である。この上限では、humaneval+ は正しさよりも「考えが 1024 トークンに収まるか」を測っている。上限を上げて測り直すまで、この差を MTP による品質の低下とは判断しない。

## 次に確かめること

1. `decode.max_tokens=4096` の decode（N = 0 と N = 1）。N ≥ 2 の計測の前提（手順 §7、#58454）。
2. humaneval+ を、コードの出力の上限を上げて（`quality.code_max_tokens`）N = 0 と N = 1 で測り直す。
3. N = 2、3 の計測。1 ステップの時間の伸びが下書き 1 トークンあたり約 7 ms のまま続くかどうかと、受理長の伸びを比べて、最適な N を決める。
