# sparkDash で測った値

日付は 2026-09-30 JST。他のレシピが公表値に使っている [sparkDash](https://github.com/MiaAI-Lab/sparkDash) (MIT) で、
このリポジトリの構成を測った。MiaAI-Lab は公表値を sparkDash で測っており (レシピの README の「measured with sparkDash」)、
knapcio も公表の表に sparkDash 1.8.8 の値を使っている。実機操作は対話側が行った。

`bench/` の値とは、入力、出力の長さの決め方、思考の扱い、送り先が違う。成功の基準の判定は、これまでどおり `bench/` で行う。
この記録の値は、sparkDash で測った公表値と並べるためのものである。

## 測り方

| 項目 | 内容 |
|---|---|
| 道具 | head (`10.0.1.60`) に入っている sparkDash 1.8.6 (`f2ec8fe`)。画面のボタンと同じ処理を、その REST API から呼んだ。sparkDash の設定と版は変えていない |
| 送り先 | OpenAI 互換の `/v1/chat/completions`。sparkDash は、同じ機械のサーバーには `127.0.0.1` で接続する。このリポジトリの推論サーバーは `10.0.1.60` だけで待ち受けるので、計測の間だけ head に中継 (`127.0.0.1:8000` → `10.0.1.60:8000`) を置いた |
| decode | 構造化 (1 から 200 まで数える)・散文・コードの 3 種類を、同時 1 本と 2 本で各 1 回。温度 0、`top_p` 1、出力 400 トークン (`min_tokens` と `ignore_eos` で必ず 400 まで生成させる)。値は (出力トークン数 − 1) ÷ (最後のトークン − 最初のトークン)。出力トークン数は、サーバーが返す `usage` の値。同時 2 本は、1 本あたりの中央値と合計 |
| prefill | 8k・32k・128k を各 1 回 (同時 1 本)。入力は、使い捨ての識別子の後ろを単語 `the` の繰り返しで埋めた文。値は、入力トークン数 ÷ 最初のトークンまでの時間 |
| 思考 | sparkDash は、すべての要求に `chat_template_kwargs` の `enable_thinking: false`、`thinking: false`、`thinking_mode: "disabled"` を付ける。`reasoning_effort` は送らない |
| クロックの上限 | GPU `300〜1800 MHz`、X925 3.0 GHz。計測の間の GPU の実クロックの最高は 1,774〜1,781 MHz。2 台とも `NV_ERR_NO_MEMORY` は 0 件 |

## このリポジトリの構成での思考の扱い

このリポジトリの構成は、重みに付いている標準のチャットテンプレートを使う。

- **テンプレート**: `enable_thinking` を読まず、必ず思考を始める。深さは `reasoning_effort` で決まり、送られなければ既定 (最大) になる。
- **推論のパーサー (`glm47`)**: `enable_thinking: false` を受けると、出力を思考と本文に分けず、すべて本文として返す。
- **結果**: sparkDash の「思考オフ」では思考は止まらず、思考も本文として数えられる。どの要求でも、思考として分けられたチャンクは 0 だった。

sparkDash と同じ要求 (構造化、出力 120 トークン) の出力の冒頭:

| 構成 | 出力の冒頭 |
|---|---|
| 既定 (深さは最大) | 「The user wants me to count from 1 to 200 … Let me generate the numbers 1 through 200 separated by spaces.」のあとに数字 |
| low | 「Output numbers 1-200.」のあとに数字 |

公表値の「thinking off」に近づけるため、サーバーの既定の深さを low にした一時構成でも測った。
この一時構成は、`--default-chat-template-kwargs '{"reasoning_effort":"low"}'` だけを足したもので、`serving/var/` に置いた。
要求側の `chat_template_kwargs` が優先され、送られない `reasoning_effort` にだけ既定が効く。

## 結果 (このリポジトリの構成、KV 4 GiB、tok/s、各 1 回)

| 項目 | 既定 (深さは最大) | low |
|---|--:|--:|
| 構造化 同時 1 本 | 60.01 | 60.39 |
| 構造化 同時 2 本 (1 本あたり / 合計) | 40.41 / 77.95 | 45.92 / 91.83 |
| 散文 同時 1 本 | 42.38 | 42.74 |
| 散文 同時 2 本 (1 本あたり / 合計) | 28.40 / 55.25 | 29.24 / 57.71 |
| コード 同時 1 本 | 55.18 | 58.23 |
| コード 同時 2 本 (1 本あたり / 合計) | 33.71 / 62.33 | 39.90 / 77.10 |
| prefill 8k (最初のトークンまで) | 1,451 (5.7 秒) | 1,435 (5.7 秒) |
| prefill 32k | 1,583 (20.7 秒) | 1,588 (20.6 秒) |
| prefill 128k | 1,568 (83.6 秒) | 1,594 (82.3 秒) |

- **low の効き方**: 同時 1 本ではほとんど変わらない。同時 2 本では、構造化とコードが 1〜2 割速かった。思考が短いぶん、ドラフトが当たりやすい出力が増えたためと見る (確かめてはいない)。
- **prefill が `bench/` より高く出る理由 (確かめていない)**: sparkDash の cold 32k (約 1,585) は、`bench/` の cold 32k (1,331、[記録](2026-09-30-mmastrac-32k-same-conditions.md)) より約 2 割高い。
  - sparkDash の入力は、同じ単語の繰り返しである。
  - そのため MoE で選ばれる専門家が少数に偏り、読み込む重みが減って速くなる、という見方である。
  - この構成の cold prefill は、GPU の時間の約 4 割が専門家の計算である ([プロファイル](2026-09-30-prefill-profile-batched-tokens.md))。
- **回数**: どの値も 1 回ずつで、ばらつきはわからない。

## 他のレシピ

同じ sparkDash、同じ 2 台、同じクロックの上限で、各レシピの既定の構成を測った。
sparkDash は登録された 8000 番に接続するので、計測の間だけ head の中継の行き先を、各レシピの API の番号に向けた。

### mmastrac NVFP4 + DFlash2 (既定の構成)

- **構成**: [9 月 30 日の記録](2026-09-30-mmastrac-32k-same-conditions.md) の A と同じ既定の構成。`compose/.env` に `TP=2`、`compose/glm53.yaml` だけで、実験的な上書きはなし。DFlash2 (`k=7`) を使う。
- **計測の時間帯**: 18:43〜18:48 JST。
- **思考の扱い**: mmastrac の独自のチャットテンプレートは、`enable_thinking: false` を「思考を浅くする」と読む。sparkDash と同じ要求 (出力 120 トークン) では、思考は「Output 1–200 space-separated.」の 1 文 (8 トークン) だった。推論のパーサーは、これを本文と分けて返した。sparkDash の decode の値は、思考と本文を合わせた出力トークン数で数える。
- **計測の間の状態**: GPU の実クロックの最高は 1,774〜1,781 MHz。`NV_ERR_NO_MEMORY` は、worker で 2 回出た。

| 項目 | mmastrac | 参考: このリポジトリの構成 (low) |

- **decode の比べ**: 構造化とコード (ドラフトが当たりやすい入力) は、mmastrac のほうが速い。散文は、このリポジトリの構成のほうが速い。
- **`bench/` とは順位が入れ替わる**: `bench/` (`fast`、コード・散文の課題、思考は既定) では、コード・英語はこのリポジトリの構成が 45.0、mmastrac が 33.2 だった。物差しによって順位が入れ替わる。
