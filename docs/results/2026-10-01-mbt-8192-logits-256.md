# `--max-num-batched-tokens` 8192 と indexer の logits の上限 256 MB (2026-10-01)

日付は 2026-10-01 JST。推奨の構成 `glm53-tp2-mtp3-marlin` について、2 つの設定を同時に変えて入力の処理を測った (issue #129、#169)。

- `--max-num-batched-tokens` を 8192 にする。
- 環境変数 `VLLM_SPARSE_INDEXER_MAX_LOGITS_MB` を 256 にする。

測る前の構成は、KV を 1 台あたり 4 GiB に固定し、既定の思考の深さを low にし、`--max-num-batched-tokens` を 4096 にしていた ([4096 の記録](2026-10-01-mbt-4096.md))。
起動の前に、2 台のページキャッシュを捨てた。クロックの上限は GPU `300〜1800 MHz`、X925 3.0 GHz である。実機の操作は対話側が行った。

## 結論

- **この 2 つの設定を採った。** 入力の処理は、32k・64k・128k のどれでも、4096 より約 1 割速かった。
  - cold 32k は 1,448 → 1,614 tok/s (+11%)、cold 128k は 1,429 → 1,576 tok/s (+10%) になった。
  - 入力の処理 (cold 32k) は、成功の基準 2,000 tok/s の 81% になった (4096 では 72%)。
- **8192 だけで起きた問題は、上限を 256 MB に下げると起きなかった** ([8192 の記録](2026-10-01-mbt-8192-128k.md))。
  - 8192 だけのときは、cold 128k が 1,141 tok/s に落ちた。head では `NV_ERR_NO_MEMORY` が出て、128k を流した後は 32k も遅くなった。
  - 今回は 2 回の起動で、cold 128k が 1,576 tok/s だった。128k を流した後の 32k も 1,612 tok/s で、落ちなかった。
  - `NV_ERR_NO_MEMORY` は、2 台とも 0 件だった。preemption も 0 回だった。
- **原因の見立て**: 固定した vLLM の indexer は、prefill の logits (fp32 の [行, 文脈 ÷ 4]) が上限 (既定 512 MB) を超えないように、行の向きに小分けにする。
  - 試した組み合わせの中で、小分けが 2 回以上になるのは 8192 × 128k だけである。
  - `vllm/models/glm5next/nvidia/sparse_indexer.py` の書き方では、2 回目の計算の間も 1 回目の logits が残る。このため、ピークは約 1 GiB になる。
  - 上限を 256 MB にすると、8192 × 128k の小分けは 256 MB × 4 回になり、ピークは 4096 × 128k と同じ約 512 MB になる。
- **分かっていないこと**: 上限なしのときに、約 512 MB の上乗せで、なぜメモリの確保に失敗したのかは確かめていない。
  - 上限を 256 MB にした起動では、head の空きメモリー (MemFree) は、最小でも 5.4 GiB あった。
  - 上限なしの起動では、空きメモリーを測っていない。
  - 分かっているのは、上限を下げると失敗が起きなくなり、速さも落ちなくなる、ということまでである。

## A. 探り: cold 32k・128k (各 3 回) と、128k の後の 32k (2 回)

一時構成 `glm53-tp2-mtp3-marlin-mbt8192-lg256` で測った。`serving/var/` に置き、計測の後に消した。2 台の空きメモリーも、1 秒ごとに記録した。
要約は [32k・128k](20261001T110920Z-p2-nope-tp2-mtp3-h9gan9/summary.md) と [128k の後の 32k](20261001T111635Z-p2-nope-tp2-mtp3-2w4ezd/summary.md)。

| 条件 | 4096 | 8192 (上限なし) | 8192 + 上限 256 MB |
|---|--:|--:|--:|
| cold 32k | 1,448 | 1,605 | 1,609 (1,606〜1,612) |
| cold 128k | 1,429 | 1,141 | **1,576** (1,573〜1,577) |
| 128k の後の cold 32k | — | 1,146 (sparkDash) | **1,612** (1,612〜1,613) |

- 空きメモリー (MemFree) の最小は、head が 5.4 GiB (起動の直後は 6.5 GiB)、worker が 7.5 GiB だった。
- ページキャッシュ (Cached) は、2 台とも計測の間に 3 GiB から約 7 GiB に増えた。

## decode

この構成では decode を測っていない。

- decode は 1 ステップに流すトークンが 4 つと少ないので、`--max-num-batched-tokens` の影響を受けない。8192 でも、2048 とばらつきの範囲で同じだった ([記録](2026-10-01-mbt-8192-128k.md))。
- logits の上限は、prefill の小分けにしか使われない。
- README の decode の値と、sparkDash の decode の欄は、そのままにした。
