# K2 第 3 段: FP8 にしていた層を NVFP4A16 にした重み（`k2s3`）

日付は 2026-09-28 JST。[ADR 0007](../decisions/0007-k2-stage2.md) の続きで、`k2s2b` の FP8 の層（489 モジュール）を NVFP4A16（重みだけ NVFP4）にした。目的は、コード・英語の decode を基準の 45 tok/s に届かせることである（`PLAN.md` §3）。
2 つの上限（GPU 1800 MHz、X925 3.0 GHz）は両台で効いていた。実機操作は対話側が行った。

## 要約

- **追記（2026-09-28 11:30 JST）: 重み `k2s4` に vLLM の `--moe-backend marlin` を足すと、確認の段でコード・英語が 45.0 tok/s になり、基準の 45 tok/s に届いた**（[下の節](#k2s4--marlin確認の段n--3)）。壊れは見つからなかった。
- **探り（出力 128 トークン、MTP の N = 3）:**
  - コード・英語は 42.4 → **48.0 tok/s**（`k2s2b` から +13%）。
  - ほかの 3 条件も 7〜10% 速くなった。
- **確認の段（出力 256 トークン、N = 3）:**
  - コード・英語は 37.8 → **42.1 tok/s**。**基準の 45 tok/s には約 7% 届かない。**
  - 散文・日本語は 39.7 tok/s（基準 30 を満たす）。
- 受理長はほぼ変わらない（探りで 2.97〜3.68、確認で 2.83〜3.14）。NVFP4 にしても、下書きの当たり方は落ちていない。
- 壊れは見つからなかった。
  - 確認の段の toolcall は 9 / 10。投機なしの基準の回は 7 / 10 で、入れ替わった 2 問は、どちらも「不正解 → 正解」だった。
  - humaneval+（上限 2048）は 10 / 10。needle 8k・32k は正解。印は 0 件。
- MTP の N = 4 は、確認の段で N = 3 より遅かった（code/en は 37.8 tok/s）。既定は N = 3 のままとする。

## 作った重み

| 項目 | 値 |
|---|---|
| 重み | `k2s3`。道具 `experiments/k2-quant`（commit `90b8a71`）の `--preset k2s3` |
| 形式 | NVFP4A16。E2M1 の 4 bit を 2 つずつ詰め、16 要素ごとの FP8 E4M3 のスケールと、テンソルごとの FP32 の全体スケールを持つ。まとめた層の組は全体スケールをそろえた |
| 変換 | 2 台それぞれ、約 10 分。2 台の道具のマニフェストはバイト単位で一致した。19 ファイル、186,444,563,117 バイト |
| 照合 | `serve verify` で 2 台とも合った |
| 重ね合わせ | `k2s2b`（PR #81） |
| 起動 | 両台で重みのファイルのページキャッシュを捨て（root 不要、PR #90）、`--load-format instanttensor` で起動 |

変換の前に、道具の形式の解釈を、元の重みの本物の NVFP4 の専門家（層 10、専門家 5、`down_proj`）で確かめた。戻して詰め直すと、次のとおりだった。
- 全体スケール（26496）とブロックのスケールは、本物と一致した。
- 戻した値も一致した。
- 詰めたバイト列は 6.6% が違った。値 0 の符号の付け方の違いで、戻した値は同じである。

## MTP の層まで NVFP4A16 にした重み（`k2s4`、確認の段、N = 3）

`k2s3` のプロファイルで、MTP の層（層 45）が BF16 と FP8 のまま残っていた（1 ステップあたり、FP8 の専門家 4.6 ms、BF16 の GEMV 1.9 ms）。そこで、層 45 の MLA の射影と FP8 の専門家も NVFP4A16 にした（道具 commit `949fb93`、`--preset k2s4`、1357 モジュール、19 ファイル、183,128,347,612 バイト。2 台のマニフェストは一致した）。

要約は [decode](20260928T013106Z-p2-nope-tp2-mtp3-sngojd/summary.md)・[concurrency](20260928T013643Z-p2-nope-tp2-mtp3-9wiz5k/summary.md)・[quality](20260928T013904Z-p2-nope-tp2-mtp3-gmqf6n/summary.md)。

| 条件 | `k2s3` | `k2s4` | `k2s4` の受理長 |
|---|---:|---:|---:|
| `decode/code/en` | 42.144 | 42.326 | 3.07 |
| `decode/code/ja` | 39.180 | 39.123 | 2.89 |
| `decode/prose/en` | 40.669 | 38.864 | 2.98 |
| `decode/prose/ja` | 39.672 | 36.697 | 2.78 |

| 同時の本数 | `k2s3` の 1 本あたり | `k2s4` の 1 本あたり |
|---|---:|---:|
| 1 | 38.018 | 22.041 |
| 2 | 25.777 | 12.596 |
| 4 | 12.499 | 7.991 |

- **MoE の実装が既定（主の層は `FLASHINFER_CUTLASS`）のままでは、`k2s4` は効かない。** コード・英語は +0.4% で、ぶれの範囲である。Marlin にそろえた回は、下の節のとおり速くなった。散文は 4〜8% 遅くなった。
- 入力が約 2,000 トークンの concurrency では、大きく遅くなった。1 本でも、最初のトークンまでが 1.3 → 3.1 秒、decode が 38 → 22 tok/s である。受理長は変わらない（2.76、`k2s3` は 2.77）。
- 記録によると、MTP の層の専門家は NVFP4A16（重みだけ 4 bit）なので、MoE の実装は `MARLIN` が選ばれた。主の層の専門家（元の重みの NVFP4、W4A4）は `FLASHINFER_CUTLASS` のままである。ただし、主の層の MoE も `MARLIN` にした回（下の節）では、長い入力でも遅くならなかった。`MARLIN` を使うこと自体は、遅くなった理由ではない。理由は切り分けていない。
- 品質の壊れは無かった。toolcall は 9 / 10（投機なしの基準の回と比べ、入れ替わった 2 問はどちらも「不正解 → 正解」）、humaneval+ は 10 / 10、needle は 2 / 2、印は 0 件。

## 主の MoE の実装を Marlin にした回（`k2s3`、`--moe-backend marlin`、確認の段、N = 3）

`k2s3` のプロファイルでは、主の層の MoE（`FLASHINFER_CUTLASS`。活性も 4 bit にするまとめた GEMM）が GPU の時間の 49% を占めた。decode では 1 回に流れるトークンが少ないので、重みだけ 4 bit で活性は BF16 のままの Marlin の MoE のほうが速いかを見た。重みは `k2s3` のまま、vLLM の引数 `--moe-backend marlin` だけを足した。起動の記録では、主の層の NVFP4 の MoE も、MTP の層の FP8 の MoE も `MARLIN` が選ばれた。

要約は [decode](20260928T015745Z-p2-nope-tp2-mtp3-jsuvtt/summary.md)・[concurrency](20260928T020236Z-p2-nope-tp2-mtp3-ozss6w/summary.md)・[quality](20260928T020932Z-p2-nope-tp2-mtp3-wi3zyt/summary.md)。quality は、起動し直した別の回である。

| 条件 | `k2s3` | `k2s3` ＋ Marlin | 伸び | 受理長 |
|---|---:|---:|---:|---:|
| `decode/code/en` | 42.144 | 43.789 | +3.9% | 3.10 |
| `decode/code/ja` | 39.180 | 41.836 | +6.8% | 2.88 |
| `decode/prose/en` | 40.669 | 44.161 | +8.6% | 3.02 |
| `decode/prose/ja` | 39.672 | 40.814 | +2.9% | 2.76 |

| 同時の本数（入力 約 2,000 トークン） | `k2s3` の 1 本あたり | ＋ Marlin の 1 本あたり | `k2s3` の合計 | ＋ Marlin の合計 |
|---|---:|---:|---:|---:|
| 1 | 38.018 | 44.888 | 38.318 | 45.242 |
| 2 | 25.777 | 27.386 | 43.913 | 41.175 |
| 4 | 12.499 | 14.713 | 41.364 | 43.602 |

- **4 条件とも速くなった。** コード・英語は 43.8 tok/s で、基準の 45 tok/s にはまだ約 3% 届かない。
- 受理長は変わらない。1 ステップが短くなった分である。
- 長い入力でも遅くならなかった。最初のトークンまでは 1.36 秒（`k2s3` は 1.29 秒）。
- 壊れは見つからなかった。toolcall は 9 / 10 で、10 問とも `k2s3` と同じ結果だった。humaneval+（上限 2048）は 10 / 10、needle 8k・32k は正解、印は 0 件。
- **Marlin を採る。** 活性を 4 bit にしないので、精度の面でも元の設定より不利にならない【推測。量の多い比較は P8 で行う】。

## `k2s4` ＋ Marlin（確認の段、N = 3）

主の層も Marlin にすると、`k2s4` の MTP の層（NVFP4A16）と MoE の実装がそろう。重み `k2s4` に `--moe-backend marlin` を足して、同じ確認の段を流した。要約は [decode](20260928T021952Z-p2-nope-tp2-mtp3-isi3vr/summary.md)・[concurrency](20260928T022434Z-p2-nope-tp2-mtp3-5afst7/summary.md)・[quality](20260928T022550Z-p2-nope-tp2-mtp3-ib6qny/summary.md)。

| 条件 | `k2s3` | `k2s3` ＋ Marlin | `k2s4` ＋ Marlin | 受理長 |
|---|---:|---:|---:|---:|
| `decode/code/en` | 42.144 | 43.789 | **45.021** | 3.05 |
| `decode/code/ja` | 39.180 | 41.836 | 43.941 | 2.91 |
| `decode/prose/en` | 40.669 | 44.161 | 46.267 | 2.95 |
| `decode/prose/ja` | 39.672 | 40.814 | 42.176 | 2.75 |

| 同時の本数（入力 約 2,000 トークン） | 1 本あたり | 合計 |
|---|---:|---:|
| 1 | 44.802 | 45.155 |
| 2 | 27.235 | 45.846 |
| 4 | 15.145 | 46.474 |

- **コード・英語は 45.0 tok/s で、基準（45 tok/s 以上）に、確認の段の少ないサンプルで届いた。** 余裕はほぼ無い。量の多い計測での判定は P8 で行う。
- `k2s4` の MTP の層の効き目は、MoE の実装を Marlin にそろえると出た（`k2s3` ＋ Marlin より 2.8〜5.0% 速い）。
- 長い入力でも遅くならない。最初のトークンまでは 1.39〜1.40 秒。
- 同時 2 本の 1 本あたりは 27.2 tok/s で、基準（30 tok/s）にはまだ届かない。
- 壊れは見つからなかった。toolcall は 7 / 10 で、10 問とも投機なしの基準の回と同じ結果だった（`k2s3` の回で「不正解 → 正解」に入れ替わった 2 問が、基準の回と同じ不正解に戻った。この 2 問は、第 2a・2b 段の回でも不正解である）。humaneval+（上限 2048）は 10 / 10、needle 8k・32k は正解、印は 0 件。
- **既定の候補を、`k2s4` ＋ `--moe-backend marlin` とする。**
