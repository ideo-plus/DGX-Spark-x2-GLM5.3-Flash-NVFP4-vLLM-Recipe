# mmastrac NVFP4 + DFlash2 の実機測定

## 対象

- 日付: 2026-09-29 JST
- 2 台の DGX Spark、TP=2
- [mmastrac/glm-5.3-flash-4x-gx10](https://github.com/mmastrac/glm-5.3-flash-4x-gx10) の commit `3df22b8` に、
  上流の直し [`4b95b57`](https://github.com/mmastrac/glm-5.3-flash-4x-gx10/commit/4b95b57) (#24) だけを当てたもの
- 重み: `nvidia/GLM-5.3-Flash-NVFP4` の revision `09b04e5e74bca08ca8549fc736d4cdd8624bfde3`
  (44 ファイル、204,476,278,041 バイト。両台で名前と大きさが Hugging Face の一覧と一致することを確かめた)
- 推測: DFlash2 `k=7` (adaptive-k)。MoE は `flashinfer_cutlass`、KV は FP8 で 8 GiB に固定
- 上書き: `arx`、`snapshot`、`adaptive-k`、`fp8`、`megamoe`、`fixes`、`sp` (RecoverSSM は使わない)
- イメージ: レシピの `image/` から head で組み立てた `spark-glm53:v9` (`sha256:615623170a62…`)。両台で同じ
- API は head の `:8002`。対象サーバーの定義は `mmastrac-tp2-dflash2`
- ベンチマーク: decode と同時処理は `fast`、入力の処理は `fast` から 128k を外した設定 (8k・32k、各 5 回)。
  このリポジトリの構成を測ったときと同じ

DFlash2 の下書きモデルは非商用の条件付きなので、このレシピの部品には使えない。ここでは比べるためだけに、
公開のレシピをそのまま動かした。

## 結論

- **decode・同時処理・8k の入力の処理は、このリポジトリの構成より速かった。** コード・英語 48.6 tok/s (こちらは 45.0)、
  同時 2 本の 1 本あたり 32.1 tok/s (27.2)、cold 8k 2,773 tok/s (1,364)。
- **cold 32k は測れなかった。** 32k の要求は 5 回ともサーバーの待ち行列から出ず、120 秒で時間切れになった (下の「32k の要求」)。
- decode は、どの構成も思考だけで出力の上限 (256 トークン) に達した。比べているのは思考を含む全出力の生成速度である。

## 32k の要求

- 慣らしの 1 回 (短い入力) は通った。32k の本番の要求は、5 回とも最初のイベントが 120 秒届かず、時間切れになった。
  5 回続いたので、ベンチマークの道具が計測を止めた (状態 `aborted`)。
- サーバーの統計では、要求が `Waiting: 1 reqs` のまま、KV の使用率 0% で、実行に入らなかった。
  8k の要求では KV の使用率は 11.4% だったので、KV の容量が足りないとは見ていない。
- サーバーは落ちず、`/v1/models` は応答し続けた。
- 原因は調べていない。うまく動かない部分は深追いしない、という計測者の判断による。

## 起動のつまずき

- 最初の起動は、Codex が流用した RedHatAI 版の重み (`RedHatAI/GLM-5.3-Flash-NVFP4`) で、重みの読み込み中にメモリが足りなくなった。
  レシピが指定する NVIDIA 版の重みを取り直した。
- `3df22b8` のままでは、vLLM の初期化が `ModuleNotFoundError: No module named 'vllm.models.glm5next.common.tp3pad'` で落ちた。
  `fixes.yaml` が差し込むコードが、TP=3 用の `tp3.yaml` でしか入らないモジュールを、必ず読み込んでいた。
  上流が同じ日に `4b95b57` で直していたので、その 1 ファイル (`experimental/fixes/model.py`) だけを両台に当てた。
  イメージは作り直していない。
- 直したあとの起動は、コンテナの起動から要求を受け付けるまで約 15 分だった。
