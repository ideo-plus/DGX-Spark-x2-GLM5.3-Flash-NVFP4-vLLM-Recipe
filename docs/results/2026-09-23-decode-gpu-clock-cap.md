# GPU クロック上限の決定と初回の decode・品質計測

日付は 2026-09-23 JST。[TP=2 の初回起動と短い応答](2026-09-23-patched-tp2.md) の後、
[初回計測の手順](../vllm-baseline/initial-benchmark-procedure.md) に従って decode を測った。
計測の途中で、発熱と電力の上振れを先に抑えるべきと計測者が判断した。
そのため既定クロックの計測を中断し、全力負荷で GPU クロックの上限を決めてから測り直した。
実機操作は対話側が行った。

## 1 回目: 既定クロック（中断）

全 16 関門を通過し、10:25 JST に起動、`status=ready` まで約 9 分だった。
今回のコンテナに帰属する NCCL ログは `nccl.spark-153d.251.log` と `nccl.spark-5083.192.log`。
各台で NCCL の初期化は 1 回、経路確定行はすべて IB、Socket は 0 件だった。
head の 251 は前回の試行と同じ PID で、前回分は上書きされた。前回分は前回の回収ディレクトリに残る。
`serve smoke --max-tokens 512` は英語・日本語とも HTTP 200・`end_turn` で、意味が通った。

`bench run --suite decode --profile quick` は、`decode/code/en` の 8 試行（慣らし 2 を含む）で
SIGINT によって中断した。状態は `interrupted`、失敗は 0。この計測ランは公開しない。
計測中の GPU は 62〜64℃・約 38 W・SM 2496〜2515 MHz で、減速の理由はどれも Not Active だった。

## GPU クロック上限の決定

### 方法

推論サーバーを止め、自前イメージの PyTorch で BF16 の 8192³ 行列積を 1,200 秒回し続けた。
両台で同時に実行し、10 秒ごとに次の値を読み取った。

- GPU の温度・SM クロック・電力・減速の理由・累積カウンタ
- ACPI 熱区域の最高値

条件は既定、`nvidia-smi -lgc 300,2100`、`nvidia-smi -lgc 300,1800` の 3 つ。

GB10 では減速の理由とカウンタが当てにならない。
既定クロックでは、温度の上昇に合わせて SM クロックが下がったが、理由は 0 のままだった。
公開事例にも、クロックが 600〜700 MHz に固まった状態で理由がすべて Not Active だった報告がある。
このため合格条件は実測値だけで決め、次の 4 つとした。

- SM クロックが一定
- 行列積の TFLOPS が一定
- 電力のピークが既定より低い
- ACPI 熱区域の最高値が 90℃ 未満

### 結果

| 条件（head / worker） | SM クロック (MHz) | 電力ピーク (W) | GPU 最高 (℃) | ACPI 最高 (℃) | TFLOPS | 判定 |
|---|---|---|---|---|---|---|
| 既定 | 2060〜2236 / 2086〜2229 | 91.4 / 91.0 | 82 / 80 | 92.6 / 89.4 | 91.8〜95.4 | 不合格 |
| 上限 2100 | 2086〜2093 / 2067〜2093 | 80.4 / 80.4 | 80 / 81 | 89.7 / 89.8 | 91.3〜93.0 | 余裕 0.2℃ |
| 上限 1800 | 1774〜1781 / 1781 | 54.4 / 53.7 | 73 / 71 | 80.0 / 80.1 | 79.2〜81.6 | 合格 |

3 条件とも、熱・電力による減速のカウンタは負荷中に増えなかった。
上限 2100 では GPU の最高温度がほとんど下がらず、ACPI 熱区域にも余裕がなかった。
**上限 1800 を採用した。** 90℃ まで約 10℃ の余裕があり、電力ピークは既定より約 37 W 低い。
行列積の速度は約 15% 下がる。

上限は `sudo nvidia-smi -lgc 300,1800` で両台に設定した。
再起動で既定に戻る。解除するときは `-rgc` を使う。
この 2 つの操作だけを NOPASSWD で許可する sudoers を、両台の `/etc/sudoers.d/nvidia-clock` に置いた。

### 参考にした公開情報

- 高負荷の数分後に電源が落ちる事例では、`-lgc 300,2100` で電力ピークを抑えていた。
  `-pl` は効かず、`-lgc` は効いたという。温度が同じ日でも、落ちた日だけ電力ピークが高かった
  （[nob75、2026-06-20](https://note.com/nob75note/n/ned4cc56ead79)）。
- 電源管理の不具合でクロックが 611〜702 MHz に固まり、完全な電源断で戻った事例がある
  （[fukuro_99、2026-08-24](https://note.com/fukuro_99/n/n26895f3edaad)、
  [catspawengineer、2026-08-06](https://zenn.dev/catspawengineer/articles/b1d623b2806e99)）。
  記事の復旧後の全力値（約 2185 MHz・89 W）は、今回の既定条件とほぼ同じだった。
- 2 台構成で上限 2200 を使う報告は、計測者の知人と SNS にあった。いずれも上限前後の全力負荷の比較はない。

## 2 回目: 上限 1800 で測り直し

全 16 関門を通過し、10:57 JST に起動、`status=ready` まで約 10 分だった。起動後も SM は 1768〜1781 MHz。
今回分の NCCL ログは `nccl.spark-153d.252.log` と `nccl.spark-5083.194.log`。
各台で初期化は 1 回、経路確定行 256 行がすべて IB、Socket は 0 件だった。
worker の 194 は過去の試行と同じ PID で、上書きされた。
`serve smoke --max-tokens 512` は英語・日本語とも HTTP 200・`end_turn` で、意味が通った。

`bench run --suite decode --profile quick` は 11:07〜12:06 JST に実行し、状態 `completed`、
失敗 0、`insufficient_trials` なしで終わった。
要約は [20260923T020741Z-p2-nope-tp2-smoke-fmdayl](20260923T020741Z-p2-nope-tp2-smoke-fmdayl/summary.md)。
同時実行 1、文脈長 4096、出力上限 1024、temperature 0。

| 条件 | 生成速度の平均 (tok/s) | 変動係数 | 最初のトークンまでの中央値 (秒) |
|---|---:|---:|---:|
| `decode/code/en` | 14.162 | 0.002 | 0.518 |
| `decode/code/ja` | 14.148 | 0.005 | 0.521 |
| `decode/prose/en` | 14.168 | 0.002 | 0.488 |
| `decode/prose/ja` | 13.933 | 0.010 | 0.519 |

`decode/prose/ja` には最初のトークンまで 2.445 秒の試行が 1 件あった。
平均は 0.715 秒だが、中央値は他の条件と同じ水準だった。

1 回目の中断ランにある `decode/code/en` の 6 試行と比べた。
値は生データから、2 回目の要約と同じ定義（最初から最後のトークンまで）で計算した。
既定クロックでは平均 14.647 tok/s、上限 1800 では 14.162 tok/s で、**約 3.3% 低い**。
1 回目は 6 試行だけなので、この差は参考値として扱う。
行列積の速度差（約 15%）より小さく、decode がメモリ帯域で律速されるという見方と矛盾しない。

計測中は両台とも GPU 44〜58℃、電力 20 W 以下、SM は上限で一定、減速のカウンタは増えなかった。
ACPI 熱区域の最高値は head 82.8℃、worker 73.7℃。
GPU の温度が低いのに head だけ高い。
3 回目に CPU 使用率も記録したところ、CPU 負荷は低かった（後述の「CPU 側の発熱」）。

ログを回収して所有を照合し、12:07 JST に停止した。両台ともコンテナは absent、GPU プロセスは 0 件。
負荷試験用のコンテナも残っていない。GPU クロックの上限 1800 は両台に設定したままである。

## 3 回目: 上限 1800 でツール呼び出しと code

上限 1800 を両台に入れ直した。GB10 の `nvidia-smi` には上限の設定状態が出ない。
待機中の SM クロックも 208 MHz と 305 MHz の間で入れ替わるため、上限の確認には使えない。
上限が効いているかは、負荷中の SM（1768〜1781 MHz）で確かめた。

全 16 関門を通過し、12:19 JST に起動、`status=ready` まで約 10 分だった。
今回分の NCCL ログは `nccl.spark-153d.250.log` と `nccl.spark-5083.194.log`。
各台で初期化は 1 回、経路確定行 256 行がすべて IB、Socket は 0 件だった。
`serve smoke --max-tokens 512` は英語・日本語とも HTTP 200・`end_turn` で、意味が通った。

`bench run --suite quality --profile quick` は 12:29〜13:10 JST に実行し、状態 `completed` で終わった。
要約は [20260923T032929Z-p2-nope-tp2-smoke-5fpj43](20260923T032929Z-p2-nope-tp2-smoke-5fpj43/summary.md)。
needle の 15 条件は、狙いの入力が文脈長 4096 を超えるため、送る前に飛んだ。検査済みとは扱わない。

| 条件 | 正解 / 採点対象 | 正解の割合 | 95% の区間 | 採点不能 | 要求の失敗 |
|---|---:|---:|---|---:|---:|
| `quality/toolcall` | 37 / 50 | 0.740 | 0.597〜0.854 | 0 | 0 |
| `quality/code/humaneval+` | 26 / 40 | 0.650 | 0.483〜0.794 | 0 | 0 |

判定の分類と停止理由だけを集計した。本文は読んでいない。

- **toolcall:** 50 試行すべてが `tool_use` で終わった。`--tool-call-parser glm47` によるツール呼び出しの解釈は壊れていない。
  不正解 13 件はすべて `wrong_call` だった。
  期待されたツール（`edit_file`、`move_file`、`run_tests`、`write_file`）の前に、
  `read_file`、`list_directory`、`search_files` などで下調べをしていた。
  うち 8 件は、判定で 1 回の余分な呼び出し（`extra_calls=1`）が記録された。
- **code:** 不正解 14 件はすべて出力上限 1024 トークンに達していた（`max_tokens`）。
  内訳はコードが取り出せない 10 件と、途中で切れた構文エラー 4 件。
  上限内で書き終えた 25 件はすべて正解だった。
  したがって 0.650 はコード能力よりも、思考を含む出力が 1024 トークンに収まるかを強く反映している。
  出力上限を上げた比較は未実施。

計測中の GPU は最高 58℃、電力 24 W 以下、SM は上限で一定だった。

### CPU 側の発熱

30 秒ごとに、熱区域 7 つ、コア別の使用率（直前 5 秒）、上位のプロセスを記録した
（`serving/var/nope-build-0961bbae/tp2-quality1-cpu.log`、81 点）。

| 熱区域 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---:|---:|---:|---:|---:|---:|---:|
| head 最高 (℃) | 82 | 60 | 75 | 61 | 82 | 60 | 64 |
| head 中央値 (℃) | 70 | 58 | 68 | 58 | 70 | 58 | 60 |
| worker 最高 (℃) | 73 | 60 | 73 | 61 | 71 | 60 | 65 |

熱いのは区域 0・2・4 で、待機中はどれも約 40℃ だった。
計測中の CPU 使用率は低く、コア別の中央値は大半が 0〜2%、head の高いコアでも 10〜25% だった。
上位のプロセスは vLLM と UVM。GPU は 58℃ 以下だった。
CPU 負荷も GPU 温度も低いのに区域 0・4 だけ 80℃ を超えるので、
**この熱を CPU ガバナの変更で下げられる見込みは小さい**と判断する。
熱源（メモリ、NIC、SoC の別の部位など）は、区域の名前がすべて `acpitz` なので特定できていない。

ログを回収して所有を照合し、13:11 JST に停止した。両台ともコンテナは absent、GPU プロセスは 0 件。
GPU クロック上限 1800 は設定したまま。
操作記録は `serving/var/nope-build-0961bbae/tp2-quality1-*`、
回収ログは `serving/var/20260923T032901Z-` と `20260923T041101Z-logs-p2-nope-tp2-smoke/`、
生データは `results/20260923T032929Z-p2-nope-tp2-smoke-5fpj43/` にある。

## 未確認のこと

- ACPI 熱区域 0・2・4 の熱源。CPU ガバナの変更は優先度を下げる
- code の出力上限を上げたときの正解率
- 上限 1800 での prefill・並列・長文脈・長時間運転。上限の影響は decode より大きいと見込む
- 上限を再起動後も保つ仕組み。現状は手動で設定している
