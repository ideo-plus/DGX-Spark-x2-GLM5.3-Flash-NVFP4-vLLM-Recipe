# GPU クロック上限 2200 MHz と CPU の上限なしの計測

日付は 2026-09-29 JST。構成 `glm53-tp2-mtp3-marlin` (重み `k2s4` ＋ `--moe-backend marlin`) で、
クロックの上限を緩めると速くなるかを確かめた。条件は次の 3 つである。

| 名前 | GPU の上限 | X925 CPU の上限 | 計測 |
|---|---|---|---|
| 標準 | `300〜1800 MHz` | 3.0 GHz | [9 月 28 日の記録](2026-09-28-k2-stage3.md) の値。測り直していない |
| GPU 2200 | `300〜2200 MHz` | 3.0 GHz | 今回 |
| GPU 2200・CPU 上限なし | `300〜2200 MHz` | 3.9 GHz (`cpuinfo_max_freq`) | 今回 |

CPU の上限なしの回は、計測者の指示で足した。実機操作は対話側が行った。

## 結論

- **GPU の上限を 2200 MHz に上げても、CPU の上限を外しても、decode・同時処理・入力の処理は速くならなかった。**
  標準との差は、ほとんどの条件で −7〜+7% で、向きもそろわない。回の中のばらつき
  (decode の変動係数 4〜12%) と同じ大きさである。
- 実クロックは上限まで上がっていた (GPU 2171〜2190 MHz、X925 3.9 GHz)。クロックは上がったが、速さは変わらなかった。
  GPU のクロックも CPU のクロックも、今の構成の頭打ちの原因ではない。
- 同時 2 本だけは、CPU の上限なしの回で合計が 50.6 tok/s (標準 45.8) と高かった。
  ただし回数は 2 回で、1 本あたりの値は 25.7〜35.6 tok/s とばらつきが大きい。この差は確かめられていない。
- CPU の上限を外すと、ACPI 熱区域の最高が上がった。同時処理と入力の処理の時間帯では、head が 76.2 → 77.8℃、
  worker が 73.7 → 80.4℃ だった。CPU の上限なしの decode では、head が 84.2℃ まで上がった
  (GPU 2200 の decode の回は ACPI 熱区域を読んでいないので、比べられない)。
- **上限は GPU 1800 MHz・CPU 3.0 GHz のままにする。** 緩めても速くならず、熱の余裕だけが減る。
- 2000 MHz は測らなかった。2200 MHz まで上げても速くならなかったので、その間の値では判断が変わらない。

## 条件

- 2 台の DGX Spark、TP=2。対象サーバーの定義は `p2-nope-tp2-mtp3`
- GPU の上限は両台で `sudo -n /usr/bin/nvidia-smi -lgc 300,2200` を手で設定した。
  CPU の上限は `sudo -n /usr/bin/cpupower -c 5-9,15-19 frequency-set -u 3900MHz` で外した。
  CPU のガバナは両台とも `performance` のままである
- 計測の設定: decode と同時処理は `fast`、入力の処理は `fast` から 128k を外した設定 (8k・32k、各 5 回)。
  標準の記録と同じ
- decode は思考だけで出力の上限 (256 トークン) に達した。比べているのは思考を含む全出力の生成速度で、
  標準の値と同じ定義である
- 今回の 2 つの条件の計測中、両台で重みの取得などの重い処理は止めていた

## 結果 (中央値)

### decode (各 10 回、tok/s)

| 条件 | 標準 | GPU 2200 | GPU 2200・CPU 上限なし |
|---|---:|---:|---:|
| コード・英語 | 45.021 | 45.545 | 44.856 |
| コード・日本語 | 43.941 | 45.755 | 45.224 |
| 散文・英語 | 46.267 | 46.169 | 43.113 |
| 散文・日本語 | 42.176 | 42.750 | 43.339 |

受理長は 3 つの条件とも、コード・英語で 3.02〜3.06 だった。今回の 2 つの回では JSON 指示の条件も流れた
(英語 44.390 → 42.800、日本語 41.206 → 39.316)。標準の回には、この条件がない。

### 同時処理 (入力 約 2,000 トークン、出力 128 トークン、2 回、tok/s)

| 同時の本数 | 標準: 1 本あたり (合計) | GPU 2200 | GPU 2200・CPU 上限なし |
|---:|---:|---:|---:|
| 1 | 44.802 (45.155) | 44.082 (44.429) | 43.187 (43.527) |
| 2 | 27.235 (45.846) | 27.672 (46.678) | 30.881 (50.598) |
| 4 | 15.145 (46.474) | 14.407 (45.336) | 15.161 (43.797) |

### 入力の処理 (各 5 回)

| 条件 | 標準 | GPU 2200 | GPU 2200・CPU 上限なし |
|---|---:|---:|---:|
| cold 8k | 1,364.233 tok/s | 1,462.569 tok/s | 1,400.844 tok/s |
| cold 32k | 1,326.033 tok/s | 1,307.578 tok/s | 1,237.444 tok/s |
| warm 32k (最初のトークンまで) | 3.911 秒 | 3.700 秒 | 3.637 秒 |

成功の基準の cold 32k (2,000 tok/s 以上) との差は、クロックでは縮まらない。
入力の処理は計算の多い処理だが、GPU のクロックを 22% 上げても伸びなかった。何で頭打ちになっているか
(通信、MoE のカーネルなど) は切り分けていない。

## クロック・熱・電力

両台で 5 秒ごとに `nvidia-smi` と ACPI 熱区域 (`/sys/class/thermal/thermal_zone*`) を読んだ。
値は GPU 使用率 50% 以上の標本から取った。

| 条件・計測 | ノード | GPU 実クロック (MHz) | GPU 温度 中央値 / 最高 | 電力 中央値 / 最高 | ACPI 最高 |
|---|---|---:|---:|---:|---:|
| GPU 2200・decode | head `spark-153d` | 2184〜2190 | 56 / 59℃ | 24.4 / 29.0 W | — |
| GPU 2200・decode | worker `spark-5083` | 2184〜2190 | 54 / 57℃ | 24.1 / 28.9 W | — |
| GPU 2200・同時処理と入力の処理 | head `spark-153d` | 2177〜2190 | 66 / 71℃ | 44.4 / 48.9 W | 76.2℃ |
| GPU 2200・同時処理と入力の処理 | worker `spark-5083` | 2184〜2190 | 64 / 69℃ | 44.4 / 48.3 W | 73.7℃ |
| CPU 上限なし・decode | head `spark-153d` | 2184〜2190 | 57 / 59℃ | 24.3 / 29.3 W | 84.2℃ |
| CPU 上限なし・decode | worker `spark-5083` | 2184〜2190 | 57 / 59℃ | 24.3 / 29.2 W | 73.8℃ |
| CPU 上限なし・同時処理と入力の処理 | head `spark-153d` | 2171〜2190 | 65 / 68℃ | 44.5 / 48.3 W | 77.8℃ |
| CPU 上限なし・同時処理と入力の処理 | worker `spark-5083` | 2184〜2190 | 65 / 68℃ | 44.6 / 48.4 W | 80.4℃ |

- CPU 上限なしの回は、X925 のコアの実周波数の最大が、全標本で 3.9 GHz だった。
- 減速の理由 (`clocks_event_reasons`) は、全標本で `0x0` (HW/SW の熱、SW の電力上限はどれも Not Active) だった。
  GB10 では減速の理由が当てにならない ([9 月 23 日の記録](2026-09-23-decode-gpu-clock-cap.md)) が、
  実クロックが上限に張り付いていたので、減速は起きていないと見る。
- GPU 2200 の decode の回は、ACPI 熱区域を読んでいない。

## 起動のつまずき

はじめの 3 回の起動は、worker の vLLM 初期化で CUDA の空きが必要量 (109.52 GiB) に届かず落ちた。
原因はクロックではなく、worker で動いていた別の重みの取得 (`hf download`) だった。
取得のプロセスを止めただけでは、そのプロセスの匿名メモリ約 2.3 GiB が空かない。
プロセスを終了させてページキャッシュを捨てた直後に起動すると通った。
経過は [`ops/spark-drop-caches/README.md`](../../ops/spark-drop-caches/README.md) の実機確認記録にある。
