# 0001. bench-harness の測り方

状態: 採用 (2026-09-20)。速さの計測、品質の検査、長い会話の検査の実装までを反映している。
実機で測った結果はまだ入っていない (末尾の「実機で確かめること」を参照)。

関係する要件: 11.5 (クリーンルーム)、11.6 (判断の記録)。仕様は `.kiro/specs/bench-harness/`。

## 背景

`PLAN.md` の P1 以降 (重みの選定、投機的デコード、長い会話での安定性、通信の詰め、運用) の判断は、
すべて測った値で行う計画になっている。判断が測り方に左右されないように、測り方そのものを先に固めて、
決めた理由と、それによって失うものを、ここに残す。

求めるのは「一度測れる」ことではなく、「同じ手順で何度でも測り直せて、構成どうしを同じ物差しで
比べられる」ことである。したがって、次の 3 つを他より重く見た。

- 同じ設定と種からは、いつでも同じ入力ができること (要件 11.4)
- 測り方そのもののばらつきを数字で示し、2 つの計測ランの差がその範囲かどうかを判定できること (P0 の終わりの条件)
- 失敗、中断、条件の食い違いが、結果を黙って歪めないこと

以下の「定義」は、すべて実装の中の定義である。値の名前は、要約 (`summary.json` / `summary.md`) と
比較の結果に、そのまま現れる。

## 決めたこと

### 1. 速さの定義

`/v1/messages` のストリームのイベントを受け取った直後に、解析の前に単調な時計 (`time.perf_counter_ns`)
で時刻を打つ。その時刻から、次の 4 つを出す。

| 値の名前 | 定義 | 単位 |
|---|---|---|
| `ttft_s` | 最初の `content_block_delta` の時刻 − 要求を送り始めた時刻 | 秒 |
| `decode_tps` | `(output_tokens − 1) ÷ (最後の content_block_delta の時刻 − 最初の content_block_delta の時刻)` | トークン/秒 |
| `prefill_tps` | `入力の全長 ÷ ttft` | トークン/秒 |
| `round_total_tps` | 1 回ぶんの `output_tokens` の合計 ÷ (最後のトークンの時刻の最大 − 最初のトークンの時刻の最小) | トークン/秒 |

- **最初のトークンは、種類を問わない。** `text_delta` でも `thinking_delta` でも `input_json_delta` でも、
  最初に届いた `content_block_delta` を最初のトークンとする。thinking が長いモデルで `ttft_s` が
  「本文が出るまでの時間」から離れるので、最初の `text_delta` までの時間も別に記録している
  (`first_text_ns`。参考の値で、要約の表には出さない)
- **`decode_tps` の分子が `output_tokens − 1` なのは、分母が最初のトークンと最後のトークンの間だから**である。
  最初のトークンまでの時間を含めない (要件 2.3)
- **出力が 16 トークン未満の試行は、`decode_tps` の集計に入れない。** 分母が小さすぎて値が荒れる。
  除いた件数は、印 (`too_few_output_tokens`) として条件ごとに示す。`decode_tps` の行の `n` は、
  除いたあとの数である
- **`prefill_tps` の分子は「入力の全長」**で、`input_tokens + cache_read_input_tokens +
  cache_creation_input_tokens` (欠けた項は 0) である。サーバーが `--enable-prompt-tokens-details`
  付きで起動していると `input_tokens` がキャッシュ分を引いた値に変わるので、そのままでは
  条件によって分子の意味が変わってしまう。トークン数は `message_delta` の値を正とし、
  `message_delta` が来なかったときだけ `message_start` の値を使う
- **キャッシュが効く条件の `prefill_tps` は、実効の速さである。** 分子に当たった分を含むので、
  実際に計算した量より大きく出る。要約の「表の読み方」にも同じことを書いてある
- **同時処理は、1 本と 2 本を主な結果 (primary)、4 本と 8 本を参考 (reference)** として、要約でも
  比較でも節を分ける。想定する運用が 1〜2 本 (`PLAN.md` §7) で、4 本と 8 本は余力を知るためだから。
  比較の「すべて収まった」という結論も、主な結果の行だけで決める
- **慣らしの試行は、集計に入れない。** 記録には残すが、`warmup` の印が付いた試行は要約にも比較にも
  入らない。慣らしを置く理由は 3 つある。(1) 接続の確立を `ttft_s` に混ぜないため。
  クライアントは接続を使い回すので、条件の最初の 1 回だけがこれをかぶる。(2) 生成速度の条件では、
  最初の数回が温まっていないため (既定 2 回)。(3) キャッシュが効く条件では、1 回目がキャッシュを
  温める役目そのものだから (要件 3.5)
- **対象サーバーの内部の指標は、速さとは別に、増分として記録する。** 条件ごとに前後で `/metrics` を
  読み、加工する前のテキスト (`metrics/<条件>.before.prom` / `.after.prom`) と、増分から出した
  導出値 (`metrics/deltas.jsonl`) を残す。導出値は、投機的デコードの当たり率、平均の受理長、
  生成のステップの数、1 ステップあたりのトークン、プレフィックスキャッシュの当たり率、
  KV の使用率の最大、追い出しの回数。分母が 0 のときは値なしにする。KV の使用率は Gauge なので、
  前後の差には意味がない。計測の間、`metrics_interval_s` (既定 1.0 秒) ごとに読んで最大を取る
- **`metric_map` に書く名前は、解析したあとのサンプルの名前**である。カウンターは、サーバーの出力に
  `_total` が見えなくても `_total` を付けて書き、ヒストグラムは `_sum` と `_count` に分けて書く。
  対象サーバーが違う名前を使っていても、この上書きだけで済むようにしてある

**理由**: 速さの値は、どのイベントを境目に置くかで簡単に数割変わる。定義を 1 か所に固定して、
要約と比較の両方が同じ関数を通るようにした (比較は、速さの式を書き写さず、要約と同じ
`trial_values` を使う)。サーバー側の指標を増分で併記するのは、遅いときに「測り方が悪いのか、
対象サーバーが遅いのか」を、測り直さずに切り分けるためである。

### 2. キャッシュの効き方の制御

**システムプロンプトの 1 行目に、32 桁の 16 進の識別子 (nonce) を置く。** 行の全長は識別子の長さだけで
決まるので、識別子が違っても同じでも、この行のトークン数は変わらない。

- キャッシュが**効かない**条件 (`prefill/cold/*`、同時処理) の識別子は、`(種、条件の鍵、試行の番号、
  計測ランの識別子)` から作る。計測ランをまたいでも、条件をまたいでも、試行をまたいでも重ならない
- キャッシュが**効く**条件 (`prefill/warm/*`) の識別子は、`(種、条件の鍵)` から作る。同じ前置きを
  送り続け、末尾の問いだけを変える
- 同時処理では、識別子の部品にストリームの番号を足して、1 回ぶんの n 本の先頭も重ならないようにする

**長い会話の検査 (`agent`) だけは、わざと識別子を足さない。** takt は同じ前置きを送り続けるので、
その使い方に合わせ、プレフィックスキャッシュに当てて時間を抑える。同じ種の会話は、長い段階のものが
短い段階のものをそのまま先頭に含むので、段階をまたいでもキャッシュに当たる。

その結果として、**同じ対象サーバーに 2 回目の計測ランを流すと、1 回目のキャッシュにも当たる**。
これは承知のうえである。長い会話の検査で測っているのは崩れた割合 (品質) で、キャッシュの効きに
左右されない。長い会話の試行の速さは、速さの表に入れていない。

**理由**: 調査では `cache_salt` (vLLM 独自の項目) が最も確実とされたが、採らなかった。対象サーバーを
差し替えられること (要件 1.1) が要件で、`cache_salt` を知らないサーバーはこれを黙って無視する。
「効かない条件」のつもりで測ったものが、静かにキャッシュに当たる。先頭の識別子なら、
プレフィックスキャッシュを持つどのサーバーでも確実に外れる (ハッシュは先頭のブロックから連鎖するため)。

### 3. 入力の長さの狙い方

**内容の種類ごとの「1 トークンあたりの文字数」(`chars_per_token`) を設定に持ち、文字数で狙う。**
種類は 4 つ (`prose_en`、`prose_ja`、`code`、`log`)。比は `bench calibrate` で測り直せる
(対象サーバーの `count_tokens` の口を使い、口がなければ `max_tokens=1` の要求の入力のトークン数で代える)。

- **実際のトークン数は、必ず対象サーバーの `usage` から記録する。** 速さの計算には、狙った値ではなく、
  この実測値を使う
- **狙った長さから `length_tolerance` (既定 ±5%) を超えて外れた試行には、印 (`length_off_target`) が付く。**
  印の付いた試行を集計から外すことはしない。件数を示すだけである
- **長い入力から情報を探す課題の「深さ ±5%」は、8k トークン以上の長さが前提**である。短い干し草では、
  文の切れ目の粒度が深さの誤差より大きくなる

**理由**: 手元 (Mac) にトークナイザーを置く案と、実行のたびに数えて調整する案を採らなかった。
前者は依存が重く、モデルの資産の取得が要る。後者は、対象サーバーごとに入力が変わりうる ——
比較では、同じ入力を送ることが何より大事である。比で狙えば、同じ設定から必ず同じ入力ができる (要件 11.4)。
狙いから数 % ずれるが、速さの計算には実測値を使うので、結果は歪まない。

### 4. 不確かさの出し方

**連続の値 (速さ) は、中央値と再標本化の区間で扱う。割合は、正確な二項の区間で扱う。**

- 連続の値: `n`、平均、中央値、最小、最大、標準偏差、四分位範囲 (R の type 7)、変動係数を出す。
  2 組の差の判定は、差の中央値の 95% 区間を再標本化 (10,000 回、百分位法) で求める。乱数の種は固定で、
  同じ比較は何度やっても同じ結果になる
- 割合: 正確な二項 (Clopper–Pearson) の区間。表示は両側 95%、しきい値を下回ったかの判定は片側 95% の
  上限を使う。累積確率は対数空間 (`math.lgamma`) で計算している (試行 1 万回での速さのため。厳密な
  計算との誤差は 5e-13 未満)
- **崩れが 0 件でも、「1% 未満」と言うには 1 段階あたり 299 試行が要る** (298 回では言えない)。
  これは統計の要請で、避けられない。だから設定を 2 つ用意した。`quick` (1 段階 50 回、傾向を見る) と
  `full` (1 段階 300 回、判定に使う)
- しきい値に対する判定は 3 つ。`下回った` = 片側 95% の上限がしきい値より小さい。`上回った` =
  両側 95% の下限がしきい値より大きい。`試行の数が足りない` = どちらとも言えない (崩れが 0 件なら、
  あと何回要るかを添える)
- **`試行の数が足りない` の印 (`INSUFFICIENT_TRIALS`) は、条件ではなく行ごとに判定する。**
  その行の値の数が `min_successes` に届かなければ付く。`n` の単位は行によって違う
  (`ttft_s` は本、`round_total_tps` は回) し、`decode_tps` は 16 トークン未満を除いたあとの数なので、
  条件でまとめて判定すると嘘になる。割合の行にはこの印を付けない —— 不確かさは区間そのものが
  表しているので、印で二重に示さない

**理由**: 割合が 0 に近いところでは、正規近似も Wilson の区間も使えない。正確な区間は保守的 (広め) だが、
標準ライブラリだけで書けて、「1% 未満と言い切れるか」という問いに直接答えられる。
「下回った」は片側の主張なので、片側の上限で判定するのが筋である。

### 5. 2 つの計測ランの比較の判定

**対応のある差の再標本化で判定し、許容の幅を併せて使う。**

- **対応のある比較になるのは、生成器の版と種が同じで、`(試行の番号, ストリームの番号)` の列が
  両方の計測ランで完全に同じときだけ**である。片方に失敗が 1 件あるだけで対応なしに落ちる。
  落ちたことは行ごとの警告に出す (検出力が大きく落ちて、同じ +3% の差が「収まらない」から
  「収まる」に変わってしまうため)
- 許容の幅 (`compare_tolerance`) の既定は 2%
- **「収まる」** = 再標本化した差の中央値の 95% 区間が 0 を含む、または差の割合の絶対値が許容の幅より小さい
- **「収まらない」** = そのどちらでもない
- **「判定できない」** = 値の数が判定に足りない (片側が 2 件未満)。**「収まった」ではない。**
  理由は警告に出す
- 割合の行は、2 つの両側の区間が重なるかどうかで「差が意味のあるものか」を判定する (保守的な判定)

**測ったばらつきと、偽の「収まらない」の関係** (偽のサーバーでの測定、注 2.4):

| 測り方の変動係数 | 偽の「収まらない」の出方 (試行 10 回、許容の幅 2%) |
|---|---|
| 1% | 0% |
| 2% | 1 条件あたり約 1.5% |
| 3% を超える | 20 条件で 1 件以上出る確率が 5 割を超える |

許容の幅が 0 なら、同じ分布の 2 組でも約 8% の確率で「収まらない」になる (名目は 5%)。
**「収まらない」を構成の違いだと決める前に、まず試行の回数を 20 回以上に増やして測り直すこと。**

**警告の出し分け** (要件 9.4):

- 測った値に効きうる食い違い (サンプリングの設定、出力の上限、試行の回数、道具の版、生成器の版、
  設定の名前、どちらかが未完了) は、すべて表より先の警告にする
- 名前が同じなのに `base_url` か `model` が違う対象サーバーも、ふつうの警告にする
  (「同じものを 2 回測った」証拠にならないため)
- **(参考) に落とすのは 2 つだけ**: どちらの計測ランも測っていないまとまりの設定の差と、
  `metrics_interval_s` の差。落とさないほうに寄せてある

**理由**: 入力が違えば速さも違う (投機的デコードの当たり率が内容で変わる)。対応のない比較では、
入力の違いによるばらつきに構成の違いが埋もれる。対応があれば、試行 10 回でも数 % の差を見分けられる。
許容の幅を入れたのは、ばらつきがとても小さいときに、意味のない 0.5% の差で「収まらない」と
出さないためである。

### 6. 品質の採点

**判断に迷うところは、すべて厳しい側 (正解を水増ししない側) に倒した。** あとから甘くはできるが、
甘い数字を厳しくやり直すのは測り直しになるからである。

#### ツール呼び出しの分類 (9 種類)

上から順に、**最初に当てはまった 1 つ**になる。順序を入れ替えると結果が変わる。

1. 要求そのものが失敗した → `REQUEST_FAILED`
2. ブロックが 1 つもない、または `stop_reason` が `max_tokens` → `EMPTY_OR_TRUNCATED`
3. `tool_use` がなく、本文に記法の目印が含まれる → `MARKUP_LEAKED`
4. `tool_use` のブロックがない → `NO_CALL`
5. 最初の `tool_use` の名前が、渡したツールの定義にない → `UNKNOWN_TOOL`
6. 引数が JSON として読めない → `ARGS_UNPARSEABLE`
7. 引数が、そのツールの `input_schema` に合わない → `ARGS_SCHEMA_INVALID`
8. ツールの名前か引数が正解と違う、または `tool_use` が 2 つ以上 → `WRONG_CALL`
9. それ以外 → `CORRECT`

厳しい側に倒した点:

- **引数は完全一致で比べる。** 鍵の集合も値も同じでなければ `WRONG_CALL`。定義にある任意の引数でも、
  正解に入っていないものを足せば `WRONG_CALL` である
- **JSON の型を混ぜない。** `True` と `1`、`1` と `1.0`、`"5"` と `5` は、どれも違う値として扱う
  (Python の `True == 1` に引きずられない)
- **文字列はそのまま比べる。** 大小文字、前後の空白、Unicode の正規化、経路の区切りの書き換えは、いっさいしない
- **`stop_reason` が `max_tokens` の応答は、呼び出しが完結していて正しくても `EMPTY_OR_TRUNCATED`** に
  なる。崩れた割合を膨らませる側である。呼び出しのあとに本文を続けるモデルでは、出力の上限が小さいと
  ここに落ちやすい
- 記法の目印は、`text` のブロックだけで探す (`thinking` は見ない)。モデルが人に見せる本文に
  漏れたことを見る検査だから

**採点が厳しいぶん、課題の側は公平でなければならない。** 課題の指示の文は、**正解の引数の値だけを
名指しし、任意の引数の振る舞いを匂わせない**。この決まりは後から足したものである: 最初の版では、
指示が名指しした対象のディレクトリが正解の引数に入っておらず、課題の 23% で、指示に素直に従った
呼び出しが不正解になった。生成器と採点器を別々に作るときは、「指示だけを読んだ注意深いモデルの
呼び出し」を手で組んで、本物の採点器に通して確かめること。

**崩れた割合 (`agent_break_rate`) は、`CORRECT` と `REQUEST_FAILED` を除いた 7 種類の件数 ÷
(試行の数 − `REQUEST_FAILED` の件数)。** 要求そのものの失敗はモデルの崩れではないので分母から外し、
件数を別に数える。

#### 長い入力から情報を探す課題

- **文字どおりの一致で、大小文字を区別する。** 小文字にした応答、全角のラテン文字にした応答、
  ハイフンを Unicode の異体に置き換えた応答は、設計どおり不正解になる
- 正解の前後が、**ASCII に限った境界の文字** (`0-9A-Za-z_-`) で続いていないことを確かめる。
  Python の `\w` を使わないのは、`\w` が仮名と漢字も語の文字に含むため。日本語で答えるモデルが
  「コードは SIGIL-1A2B3C4D です」と空白なしで書いたときに、常に偽陰性になった
- 引用符、逆引用符、括弧、半角の句読点で囲んだだけの応答は、正解として認める (害のない書式を罰しない)
- **同じ書式の候補を並べる応答 (shotgun) は不正解。** 正解が `PREFIX-16 進` の書式のときだけ、
  同じ接頭辞・同じ桁数の語が 2 種類以上あれば、言い当てたのではなく並べたとみなす

#### コードの課題

- 公開の課題は **HumanEval+ (EvalPlus) の `-OriginFmt` の資産、版 `v0.1.10`** に固定。SHA-256 と
  大きさを確かめてから読む。リポジトリには同梱しない
- `-OriginFmt` を選んだのは、`test` がそれだけで完結した `check(candidate)` の定義になっていて、
  **採点に EvalPlus のコードが要らない**から。既定の資産は入力の一覧と期待値を出す契約の形で、
  採点器として `evalplus` が要る
- 組み立て方: **課題の指示 (prompt) → 応答から取り出したコード → 課題の `test` →
  `check(<entry_point>)` → 検査を通ったことの印 (sentinel)**。指示を前に必ず置くのは、
  `from typing import List` のような import を書かない応答で、正しい解答が `NameError` に
  なるのを防ぐため。本体だけを書いた応答も、関数をまるごと書いた応答も、同じ組み立て方で動く
- **印 (sentinel) を `check` のあとに置き、終了コードだけでは合格にしない。** 終了コードだけだと、
  候補のコードが末尾で `sys.exit(0)` を呼べば、検査を受けずに正解になれてしまう。印はプログラムの
  中身から決まる値で、記述子 2 に直接書く。合格は「終了コード 0 かつ、標準エラーの最後の行が
  その印であること」
- **`HumanEval/32` は採点の対象から外す。** 固定した版の検査のプログラムが
  `_poly(*candidate(*inp), inp)` と書かれていて (引数の順が逆)、データセット自身の正解の解でも
  `TypeError` で落ちる。どんな応答も合格にならないので、残すと正解の割合の上限が下がる。
  採点に回す問題は、必ずこの除外を通してから数える (限りが 40 問なら、除いたあとの 40 問になる)
- **「採点できなかった」と「不正解」を分ける** (要件 5.7)。採点できなかったにしてよいのは、
  要求そのものが失敗した場合と、隔離の実行環境が使えない場合だけ。応答からコードを取り出せなかった
  場合は**不正解**である (モデルは答えたが、使えるコードがなかった)。採点できなかった件数は、
  どの割合の行でも「分母から外した数」として示す

### 7. モデルが書いたコードの隔離

**隔離できないときは動かさない。** 実行環境がなければ、コードの条件だけを理由つきで飛ばす。

起動の引数は固定で、呼び出し側から変えられない。

```
<runtime> run --rm -i --name <一意の名前> --pull never --network none --read-only
  --tmpfs /tmp:rw,size=64m --cap-drop ALL --security-opt no-new-privileges
  --memory <N>m --memory-swap <N>m --cpus <N> --pids-limit <N> --user 65534:65534
  <イメージの識別子> python -I -
```

- **イメージは、名前ではなく識別子 (`sha256:…`) で動かす。** 手元のイメージの識別子が設定の
  `sandbox.image_digest` と合わなければ、使えないものとして扱う。`--pull never` を付けて、
  **採点の途中でイメージを取りに行かせない**
- コードは標準入力で渡す。ホストのファイルを経由しない
- **時間切れのときは、コンテナそのものを止める。** `docker run` のプロセスを殺してもコンテナは
  動き続けることを確かめた (無限ループのコンテナが残った)。だからコンテナに一意の名前を付けて
  起動し、時間切れ・中断・例外のときに `kill` する。中断されたときは、コンテナが片付くまで
  (上限つきで) 待ってから中断を投げ直す
- 隔離の失敗が 3 回続いたら、コードの条件を打ち切る (ほかの条件は流れる)

**敵対的なプログラムで確かめたこと** (2026-09-20、この Mac の Docker Desktop):
ホストのパスが見えない、権限がない、ネットワークに出られない (`Network is unreachable`)、
`/` に書けない (`Read-only file system`)、`/tmp` は 64 MB まで、プロセスは 63 個まで、
2 GB の確保は終了コード 137 で不正解、標準出力と標準エラーに 200 MB ずつ流してもホストのメモリは
+0.5 MB、SIGTERM を無視するプログラムでもコンテナが残らない。

**残る危険 (この設計では防がない)**:

- **コンテナからの脱出そのものは、この設計の範囲外である。** 守っているのは「ホストのファイルと
  ネットワークに触れさせない」ことで、実行環境の脆弱性を突く攻撃は想定していない。
  流すコードは、自分たちが立てた対象サーバーが、自分たちが作った課題に答えたものだけである
- Docker Desktop では、コンテナは Mac の上の仮想機械の中で動く。この境界が最後の守りになるが、
  Podman を使う場合の境界とは性質が違う。どちらを使っているかは、計測ランに記録される
  (イメージの識別子と、使った実行環境)
- 印 (sentinel) は「うっかり / 素朴な抜け道」を塞ぐもので、同じ通訳器の中で `os.write` を
  差し替えるような本気の細工までは防げない (防ぎようがない)

### 8. 出力が壊れている疑いの印

すべてのまとまりの、すべての試行に、同じ検査をかける。

- `replacement_char`: 本文 (thinking を含む) に置き換え文字 (U+FFFD) が 1 つでもある
- `repetition_loop`: `repeat_min_chars` (既定 12) 文字以上の同じ並びが、間を空けずに
  `repeat_min_count` (既定 8) 回以上続く

**印の付いた試行は、集計から外さない。** 件数を示すだけである。

- 検出は、定義 (`単位 × 回数`) と**厳密に一致**する。見た目で怪しい並びを拾う発見的な探索はしない。
  単位の長さの上限は 4096 文字
- 印を付けないのは、単位の空白でない文字が 0 種類、または英数字でない 1 種類だけのときである。
  同じ英数字の連続 (`aaaa…`、`的的的…`) には印を付ける
- **誤って拾う例がある**: 2 種類の記号が混ざる広い表の区切り行 (`|---` が 25 列以上) と、
  `0,0,0,…` のような CSV には、定義どおり印が付く。コードやログの多い出力では、印が付いても
  壊れているとは限らない。生データを見て判断すること
- ツールの引数は、置き換え文字の検査にだけかける (JSON は構造が繰り返すので、繰り返しの検査には
  かけない)

**背景**: 上流に、GB10 の TP=2 の並行バッチで非 ASCII の生成が壊れるという未解決の問題がある
(vLLM #57087)。壊れた出力が高速に出ると、速さの数字だけが良く見える。

### 9. データの扱い

- **生データは `results/` の下に残す。** 送った内容と応答の本文を含む (`PLAN.md` §7 の、計測者の
  判断による)。`results/` は git の管理の対象ではなく、計測を始める前に、道具自身がそれを確かめる。
  確かめられなければ、計測ランのディレクトリを作らずに止まる
- **公開するのは要約だけで、`bench publish` を打ったときだけ**である。`bench run` は公開しない。
  写すのは `summary.json` と `summary.md` の 2 つだけで、生データは写さない
- **要約の型には、送った内容と応答の本文を入れる項目がない。** 本文が要約に混ざらないことを、
  型で保証している
- **認証の情報は、設定に環境変数の名前だけを書く。** 値は実行時に読み、生データにも要約にも
  標準エラーにも出さない
- **計測に使うのは、自作の合成データと HumanEval+ だけ**である。業務の実データは使わない。
  合成データは、同じ種と引数からバイト単位で同じものができる

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| `evalplus` を依存に入れて採点させる | クリーンルーム (11.5) で、コードを写さず依存にも加えないと決めた。`-OriginFmt` の資産なら `test` が完結しているので、採点器が要らない |
| vLLM 同梱の計測スクリプト (`benchmarks/`) を使う | `/v1/messages` を対象にしていない。ツール呼び出しの検査がない。対象サーバーを vLLM に縛る。考え方は参考にした |
| 汎用の HTTP の負荷試験の道具に載せる | SSE のチャンクごとの時刻、トークン数、ツール呼び出しの分類を扱えない。結局ほとんどを自作することになる |
| 1 本のスクリプトで、測りながら集計する | 集計の誤りを直すたびに測り直しになる。途中で止まったときに結果が残らない |
| 公式の `anthropic` SDK を使う | チャンクが届いた時刻を自分たちで打つ必要がある。SSE を直接読むほうが、計測の意味がはっきりする |
| `/v1/chat/completions` も話す、2 種類目のクライアント | 測りたいのは takt が使う `/v1/messages` の速さ。出力の長さを固定するためだけに、口を 2 つ持たない |
| `ignore_eos` / `min_tokens` で出力の長さを固定する | `/v1/messages` の変換では設定されず、黙って捨てられる。仮に効いても、文の終わりを越えて生成させた出力は不自然で、投機的デコードの当たり率を歪める |
| 手元にトークナイザー (Hugging Face) を置いて数える | 依存が重く、モデルの資産の取得が要る。比を設定に持てば、同じ設定から必ず同じ入力ができる |
| 実行のたびに `count_tokens` で数えて長さを調整する | 対象サーバーごとに入力が変わりうる。比較では、同じ入力を送ることが何より大事 |
| `cache_salt` でキャッシュを外す | vLLM 独自の項目で、知らないサーバーは黙って無視する。効かないつもりの条件が、静かにキャッシュに当たる |
| 割合の不確かさを、正規近似や Wilson の区間で出す | 割合が 0 に近いところでは使えない。正確な区間は標準ライブラリだけで書ける |
| 中央値の差を四分位範囲と比べるだけ / 対応のない再標本化だけ | 入力の違いによるばらつきに、構成の違いが埋もれる |
| 繰り返しの検出を、発見的な探索で速くする | 定義から外れると、何を測っているか説明できなくなる。近道を入れるなら、定義どおりの総当たりと突き合わせる試験が要る |
| 探す課題で、「正解と同じ長さの語が複数あれば不正解」とする守り | ふつうの 14 文字の英単語や、たまたま同じ長さのコード名で働いてしまい、正解の 16〜27% を不正解にした。同じ接頭辞・同じ桁数だけを候補にする形に直した |
| 境界の判定に Unicode の `\w` を使う | 仮名と漢字も語の文字に含むので、日本語に隣接した正解が見つからない |
| `<think>…</think>` を `.*?` + DOTALL の正規表現で落とす | 閉じていない `<think>` が大量にある本文 (壊れたモデルの繰り返し) で二次の時間になった (500 KB で 68 秒)。目印の位置を 1 回集めて対応づける、直線の走査にした |
| 隔離に、公式の Python のイメージをそのまま使う | 164 問のうち 163 問の検査のプログラムが numpy を使う。numpy だけを足した自前のイメージにして、識別子で固定した |
| `--suite` を省いたときに、5 つ全部を流す | 品質の検査と長い会話の検査は、実機では何時間もかかる。既定は速さの 3 つにして、残りは名指しか `--suite all` で選ぶ |
| 印 (sentinel) のない、終了コードだけの採点 | 候補のコードが末尾で `sys.exit(0)` を呼ぶと、検査を受けずに正解になれる |
| 量子化前のモデルの公開値と、同じ課題で比べる | モデルカードに載っている公開値はエージェント系の課題だけで、HumanEval や BFCL の値がない。BF16 は 2 台に載らない。品質の検査は、構成どうしの相対比較に使う |
| BFCL / BigCodeBench / tau-bench を使う | BFCL は採点器を自作する手間が大きい。BigCodeBench は多数のライブラリが要る。tau-bench はこの仕様の範囲を超える (ライセンスはいずれも使える) |
| LiveCodeBench / ToolBench / Needle in a Haystack (gkamradt) の干し草を使う | ライセンスが使えない。LiveCodeBench のデータは `cc` とだけ表記、ToolBench は表記が矛盾 (研究・教育目的のみ)、gkamradt の同梱のエッセイは権利の表記なし |
| `numpy` / `scipy` を統計に使う | 記述統計、二項の区間、再標本化は標準ライブラリだけで書ける。実行時の依存を 5 つに抑えた |

## 影響と限界

- **過去の数字と比べられる範囲は、条件の鍵と生成器の版と速さの定義に縛られる。** どれかを変えたら、
  それ以前の計測ランとは比べられない
- **出力の長さは試行ごとに少し揺れる** (上限に届かずに終わる試行がある)。速さは「トークン数 ÷ 時間」
  なので値にはほとんど効かないが、早く終わる試行が 2 割を超える条件が出たら、指示の文を見直すこと
- **温度 0 でも、同じ出力が返るとは限らない** (sm121 で greedy のデコードが非決定的、vLLM #54521)。
  再現性は「同じ入力を送る」ことで担保していて、「同じ出力が返る」ことは前提にしていない
- **品質の検査は、構成どうしの相対比較にしか使えない。** 公開値との突き合わせは当面しない
- **`MARKUP_LEAKED` と `ARGS_UNPARSEABLE` は、GLM と `glm47` のパーサーの組み合わせでは出にくい。**
  サーバーの中で壊れた記法が落とされるため、`NO_CALL` と `EMPTY_OR_TRUNCATED` に現れる見込みである。
  9 種類とも実装してあるが、結果を読むときはこの偏りを念頭に置く
- **長い会話の検査は、`quick` では段階ごとに正解のツールの分布が偏る** (1 段階 50 試行)。
  段階の差に、課題の混ざり具合が混入する。判定に使うのは `full` である
- **同じ対象サーバーへの 2 回目の計測ランは、1 回目のキャッシュに当たる** (上の「2. キャッシュの
  効き方の制御」)
- **比べる計測ランは、コミットしてきれいな状態で流すこと。** 道具の版は作業木の全体を見るので、
  `docs/` や `.kiro/` の未コミットの変更でも `.dirty` が付き、比較の警告になる
