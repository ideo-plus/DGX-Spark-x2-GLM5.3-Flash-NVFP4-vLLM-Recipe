# 0006. 速さを伸ばす道筋の枝切り (P2・P3)

状態: 採用 (2026-09-25)。

## 背景

2026-09-25 時点で、エージェントの安定性（`PLAN.md` §3）は、合成の会話で基準を満たした。
20k〜120k の各段 300 試行で崩れ 0 件、崩れの割合は 1% 未満と判定されている（[記録](../results/2026-09-24-agent-20k.md)）。

一方、速さは基準に届いていない。
今の道筋（vLLM + 自前の NoPE 修正 + NVFP4、TP=2、GPU の上限 1800 / X925 の上限 3.0 GHz）の値は次のとおり。

| 条件 | 今の値 | 基準 |
|---|---:|---:|
| 生成速度（同時 1 本、code/en） | 約 14 tok/s | 60 tok/s |
| 生成速度（同時 1 本、prose/ja） | 約 14 tok/s | 30 tok/s |

検証用の構成（candidate D、`exl3-tp2`）は、code/en で 56〜66 tok/s を出している。
細かな調整で埋まる差ではないので、試す道筋を先に絞ることにした。

## 調べたこと

- **公開のレシピと一次資料の事実の調査**（#28、TAKT の `deep-research`）。
  報告は [2026-09-25-path-survey.md](../research/2026-09-25-path-survey.md)。
  クリーンルームの決まり（`PLAN.md` §2）に従い、他のレシピのスクリプト・パッチ・設定の文面は写していない。
  candidate D と `exl3-tp2` の中身も読んでいない。
- **自分たちの `bench/` で、2026-09-20 に `exl3-tp2` を外から測った結果**（`results/20260920T*-exl3-tp2-*`、Git 対象外）。
  中身ではなく、自分たちで測った事実である。

## 分かったこと

1. **投機なしの生成速度（土台の速さ）は、エンジンと重みの形式によらず 14〜15 tok/s にそろう。**
   vLLM と SGLang、NVFP4・W4A16・専門家だけの EXL3 の公開値が、どれもこの範囲に入る。
   公開されている EXL3 の重みは専門家だけを量子化していて、1 台が 1 トークンで読む量は NVFP4 と約 15% しか違わない。
2. **candidate D の速さの源は、深いドラフターである。**
   `exl3-tp2` の平均の受理長は、次のとおりだった。
   - code/en の decode: 4.6
   - humaneval+: 7.4
   - agent: 6.2〜6.5
   - prose/ja: 2.0

   下書き 3 トークンの MTP では、受理長は最大 4 にしかならない。受理長 7.4 は、ブロック 8 程度の深いドラフターでないと出ない。
   生成速度を受理長で割った「1 秒あたりのステップ数」は約 12〜13 で、今の構成（投機なしで 14 tok/s）と同じ水準である。
   4 倍の差は、予測しやすいコードの文面で、深いドラフターが 1 ステップに多くのトークンを当てることから来ている。
   散文では受理長が約 2 に下がり、candidate D でも prose/ja は 26 tok/s だった。
3. **公開値で 60 tok/s 前後以上の報告は、確認できた範囲ですべて非商用のドラフター（DFlash2、CC BY-NC-ND）を使っている。**
   ライセンスの通る部品だけで code/en 60 tok/s に届いた公開例はない。
4. **土台の速さを上げる道は 1 つだけ見つかった。** アテンション・共有の専門家・dense・lm_head まで量子化し、1 トークンで読む量を減らすことである。
   見込みは投機なしで 19〜25 tok/s（推定）。ただし、今の重みは専門家だけが NVFP4 で、残りは BF16 で読まれている。
5. **モデル付属の MTP（MIT）の公開値は、GB10 2 台 TP=2 で 20〜31 tok/s である。**
   受理長は 2.3〜2.7。MTP の 1 ステップの時間は、投機なしの 1.6〜2.0 倍になる（計算）。

## 決めたこと

### 残す道筋（上から順に進める）

| ID | 道筋 | 期待できる速さ（推定） | 手間 | 主なリスク |
|---|---|---|---|---|
| K1 | 今の構成に、モデル付属の MTP（MIT）を足す | code/en 25〜31、prose/ja 20〜30 | 小 | vLLM の MTP の既知の不具合（下書き 2 以上で文脈が 2048 を超えると壊れる #58454、同時処理で非 ASCII が壊れる #57087）。今のイメージの vLLM の版で使えるかは未確認 |
| K2 | アテンション・共有の専門家・dense・lm_head も FP8 か 4 bit で読む | 投機なし 19〜25、MTP と組んで 30〜43 | 中〜大 | 品質（KDA の射影を量子化したときの公表値がない）。読み出し以外の約 20 ms で頭打ちになるおそれ |
| K3 | ライセンスの通る深いドラフター（modal-labs の DFlash、MIT） | K2 の上に乗せて code/en 40〜58 | 中 | 学習データが公表されていない。LICENSE の著作権者の欄が Z.AI。vLLM の対応は PR（#56983、#55682）待ち。GB10 での実績がない |

- **K1** は、手間が小さく、prose/ja の基準（30 tok/s）に近づける本命である。最初に実機で測る。
- **K2** は、K1 の計測と、今の構成の 1 トークンの時間の内訳（プロファイラー）を見てから、進めるかを決める。
- **K3** は、ライセンスの判断が済み、vLLM の対応がマージされてから試す。
  SGLang（上流のままでは GB10 で起動できない）で先に試すことは、K3 を早く測るための条件付きの手段にとどめる。

### 切る道筋

| 道筋 | 理由 | 見直す条件 |
|---|---|---|
| vLLM + EXL3 のプラグイン | 上流に EXL3 がない。主流のプラグインは AGPL。公開例は専門家だけの EXL3 で、読む量は約 15% しか減らない | K2 で FP8 や NVFP4 の品質が足りず、5〜6 bit が要るとき |
| W4A16（Marlin） | 専門家のカーネルを替えても、土台の速さは変わらない | K1 の中で、カーネルの選択肢として必要になったとき |
| PP=2 | vLLM の main で止められている。2 台の PP は decode を速くしない | — |
| TensorRT-LLM | GLM-5.3-Flash の PR が未マージで、sm_121 の経路がない。要判断のライセンスが最も多い | 対応がマージされ、SM120/121 に対応したとき |
| llama.cpp の 2 台 | テンソル分割の対象外で、2 台は層の分割だけになる | — |
| ExLlamaV3 単体 | TP が 1 台のホストの中だけ | 上流が複数ノードの TP に対応したとき |
| ktransformers | x86 と 350 GB のメモリが前提 | — |
| MXFP4 | GB10 での実績がない。NVFP4 との差は読む量で約 6% 以下 | — |
| 1 台での運用 | 約 2.7 bpw で品質が落ちる（KLD 0.38） | 品質の基準を下げてよいと判断されたとき |

### 設計の変更（K1 のため）

`.kiro/specs/vllm-baseline/design.md` の 6.7（「最初は投機的デコードなし。投機の指定を持つ構成を断る」）は、
「P3 で、この検査を構成ごとの許可に変える」と予定していた。
K1 でこの予定どおり、構成ごとに投機的デコードを許すように変える。
投機を許さない構成（`p2-nope-tp2-smoke`、`p2-nope-tp2-full`）では、これまでどおり断る。

## 未決の事項

1. **成功の基準の見直し。** code/en の 60 tok/s は、深いドラフターがある前提の値である。
   ライセンスの通る部品だけで届く根拠は、まだない。K1 と K2 を測ってから、基準を見直すかを決める。
2. **ライセンスの判断。**
   - CuTe DSL（NVIDIA の EULA）。vLLM と SGLang の道筋すべてに関わる。
   - modal-labs の DFlash の学習データと、LICENSE の著作権者の欄。
3. **調査が推測の材料にした、candidate D の作成者のリポジトリの題（メタデータ）の扱い。**
   本文は開いていない。`PLAN.md` §2 の範囲に入るかを判断する。

## 採らなかった案

- **エンジンや形式を片端から試す。** 土台の速さがそろうことが分かったので、効果の見込みが小さい。
- **非商用のドラフター（DFlash2）を使う。** `PLAN.md` §2 のライセンスの条件に反する。

- K1 の実測値が、見込み（code/en 25〜31）から大きく外れたとき。
- vLLM の #56983（DFlash）や #57171（GLM-5.3-Flash の PP）がマージされたとき。
- ライセンスの判断の結果が出たとき。
