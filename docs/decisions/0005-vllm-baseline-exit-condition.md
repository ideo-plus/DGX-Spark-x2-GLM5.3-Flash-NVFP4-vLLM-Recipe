## 背景

P1 (Baseline Procedure) は、決めた順序 (段 0 → 段 1 → 関門 A → 関門 B → 段 2 → 段 3 →
段 4) で構成を試し、いずれかで届けば計測に進み、すべて届かなければ打ち切る
(要件 8.1、8.5)。順序は、要件どおりの文言 (原案) から、障害の原因分析に合わせて組み替えた
(research.md Decision 8): アテンションの幾何 (`qk_rope_head_dim = 0`) に起因する懸念は、
重みの形式にも並列の取り方にも依らないため、重みを取得する前の 1 台の縮小起動 (段 0) で、
いちばん安くこの懸念に当たる。

要件どおりの順序のまま進めると、同じ失敗のために約 360 GiB (2 つの重みの候補) を無駄に
取得することになり、要件 8.3 (「同じ失敗を、設定を変えずに繰り返して試さない」) にも反する
(research.md Decision 8 の Rationale)。段 0 と段 1 (より新しい公式イメージでの同じ確認)
が同じ場所で失敗し、その原因が重みの形式にも並列の取り方にも依らないと示せる場合は、
重みの取得に進まずに打ち切る (要件 8.7)。

## 決めたこと

### 1. 終わりの条件 (要件 10.6)

**1 つ以上の構成で起動し、`bench` の計測を一通り流せたこと。または、計測者が改めた条件。**

「一通り流せた」は、procedure.md 段 2.6 が定める 5 つのまとまり (`decode` / `prefill` /
`concurrency` / `quality` / `agent`) の、それぞれに要約があるか、止まった場所と理由の記録が
あることを指す (要件 7.4〜7.5)。この節は、P1 の終わりに、満たしたか満たせなかったかを
判定して埋める。計測者がこの条件を改めた場合は、改めた条件と、その理由をここに記録する。

### 2. 打ち切りのときの下書き (要件 8.5)

決めた順序の構成をすべて試しても、パッチなしでは起動できない、または計測を流し切れない
場合、procedure.md の「打ち切りの手順」に従って、次の 3 つを、この節にまとめる (この節は、
打ち切りに至った場合にだけ埋める)。

1. **止まった場所**: どの段・関門で、何が起きたか
2. **試したことの一覧**: `attempts.md` へのリンクと、要点の要約
3. **直すのに要る最小の変更の候補**: 上流の未マージの変更を含む、直せば通る見込みのある
   最小の変更

**計測者の判断なしに、推論サーバーにパッチを当てない、イメージを自分でビルドしない**
(要件 8.6)。道具 (`serve`) にも、その経路はない (`docker build` を呼ぶ経路がないことを
試験で固定。`test_plan.py` など)。

### 3. PP=2 (2 台での層の分割) の扱い (要件 8.9)

1 つ以上の構成で起動できた場合、**2 台での層の分割 (PP=2) を、代替の構成としてではなく、
TP=2 との速さの比較の候補として扱う**。P1 のうちに測るか、P5 (通信と性能の詰め) に持ち
越すかは、起動できたあとに計測者に尋ねて記録する (procedure.md「終わり」の 2)。

要件のこの改訂 (もとは「2 台での層の分割」を代替の構成の候補としていた) の理由は、
懸念の切り分け (アテンションの幾何) には PP=2 も TP=2 も同じ結果になるためで、代替には
効かない。一方、推論サーバーの公式文書が、この形の 2 台構成に PP=2 を勧めている
(research.md §d-3、§d-8)。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 要件どおりの順序 (層の分割を含む代替の一覧) のまま試す | 同じ懸念 (アテンションの幾何) のために、複数の重み・複数の並列の取り方を総当たりで試すことになり、約 360 GiB の無駄な取得と、要件 8.3 (同じ失敗を繰り返さない) への違反が生じる (research.md Decision 8) |
| 「終わりの条件」を、5 つのまとまり全部が「収まる」ことにする (P0 の比較の判定と同じ基準) | P1 の目的は「対象サーバーを得る」ことであり、性能の詰めは P5 の仕事である。要件 10.6 は「一通り流せた」ことを求めており、比較の判定基準はここでは要求されていない |
| 段 0 が失敗したら、確認せずに即座に打ち切る | 上流のイメージの版によって、既知の落とし穴 (NCCL のデッドロックなど) が解消されている場合がある。より新しい公式イメージでの再確認 (段 1) を挟んでから、同じ場所での失敗を確認して打ち切る (要件 8.7) |

## 影響と限界

- 終わりの条件は「1 つ以上の構成で起動」であり、性能や品質の絶対水準を求めていない。P1 で
  得られる対象サーバーが、P2 以降でそのまま採用に値するかどうかは、この記録の範囲外である
- 打ち切りの判断そのものは、計測者が下す (procedure.md「打ち切りの手順」の 2)。この記録は、
  判断に要る材料 (止まった場所、試したこと、最小の変更の候補) をまとめるだけで、判断を
  代行しない

## 見直す条件

次のどれかをしたら、この記録を見直す。

| 変えたもの | すること |
|---|---|
| P1 が終わった場合 (打ち切りに至らず) | 「決めたこと」節 1 に、満たしたこと、満たせなかったこと、P2 以降に持ち越すことを追記する (要件 10.6) |
| 打ち切りに至った場合 | 「決めたこと」節 2 の下書きを完成させ、計測者に終わりの条件を改めるかどうかを尋ねた結果を追記する (procedure.md「打ち切りの手順」) |
| 計測者が終わりの条件を改めた場合 | 節 1 に、改めた条件と理由を記録する |
| PP=2 を測るかどうかが決まった場合 | 節 3 に、決めた内容 (P1 のうちに測る/P5 に持ち越す) と、測った場合は結果へのリンクを追記する |
