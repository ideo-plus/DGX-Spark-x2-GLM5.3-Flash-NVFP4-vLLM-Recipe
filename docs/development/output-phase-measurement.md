# 思考と本文を分けて生成速度を読む

この文書は、benchの要約から本文の生成速度を比較する人向けの説明である。
まず本文到達件数と速度の有効件数を確認し、必要な指標の定義を以下の表で確認する。
コマンド全体の使い方は[benchのREADME](../../bench/README.md)を参照。

## 要求成功と本文速度の計測成功を分ける

思考だけで `max_tokens` に達した要求は、通信に成功していても本文未到達である。
たとえばJSON条件で10試行すべてが思考だけなら、要求成功10件に対して本文速度の有効件数は0件となる。
全出力の `decode_tps` が得られていても、JSON本文の速度を測れたとは言えない。

要約には、慣らしを除く要求総数、成功・失敗と成功率の分母、本文到達、本文未到達、思考のみ、
思考あり、段階別情報不明、速度の有効件数と欠測理由を表示する。本文未到達には思考のみを含むので、
両者を加算しない。思考ありは、思考のブロックに1文字以上が届いた試行の数で、本文の有無を問わない。
JSON条件の本文到達は完全性・妥当性の採点ではない。
途中で要求が失敗した場合も、受信済みの本文到達は残るが、成功要求の速度分布からは除く。

## 全出力と段階別指標は算式が異なる

時刻は単調時計で記録する。thinkingとtextは、それぞれ空でない実データの先頭・末尾時刻、
Unicode文字数、ブロック有無を持つ。ブロック開始の文字列と複数ブロックも対象にする。
署名、ping、空delta、ツール引数、未知イベントは本文実データに数えない。

| 指標 | 算式・単位 |
|---|---|
| `decode_tps` | 従来どおり `(usage.output_tokens - 1) / ((last_token_ns - first_token_ns) / 1e9)`。思考などを含む全出力のトークン/秒 |
| `text_wait_s` | 要求送信から本文の最初の非空データまでの秒数 |
| `thinking_duration_s`、`text_duration_s` | 各段階の最初から最後の非空データまでの秒数 |
| `thinking_chars`、`text_chars` | 各段階のUnicode文字数 |
| `thinking_chars_per_s`、`text_chars_per_s` | 各段階の文字数 / 継続時間。文字/秒 |
| `thinking_retokenized_tps`、`text_retokenized_tps` | 各段階の再計数トークン数 / 継続時間。再計数によるトークン/秒 |

本文区間に、本文が始まる前の思考待ちは含めない。段階別速度の分子は最初の断片の文字も含む。
従来の全出力式の「−1」は転用しない。単一の実データや同時刻のdeltaなど、区間が0のときは
速度を不明とし、無限速度を出さない。SSEのdeltaは複数トークン分を含み得るので、個数をトークン数にしない。

本文→思考→本文など、両段階の観測区間に重複・包含がある場合、保存された先頭・末尾だけでは
区間を分離できない。この場合は両段階の継続時間、文字/秒、再計数トークン/秒を不明にし、
要約と比較に理由と件数を表示する。途中の思考待ちを本文の時間に混ぜたり、旧記録から区間を
推測したりしない。本文到達、文字数、本文までの待ち時間、再計数値は保持する。
通常の思考→本文や境界時刻が一致するだけの場合には、この制限を適用しない。

## 再計数は明示的に有効にする

サーバーが返す `usage.output_tokens` が全体だけの場合、生成時の思考・本文の内訳は不明となる。
全体の値を両側へ流用したり、断片数や文字数比で配分したりしない。

```bash
# bench/ で実行する場合
uv run bench run --target candidate-d --suite decode --profile probe --retokenize-output
```

このオプションは、終了した出力を同じサーバーの `/tokenize` で数え直す。
同種ブロックを保存順に区切り文字なしで連結し、モデル名と生文字列の `prompt`、
`add_special_tokens=false` を送る。チャットの包みを加えない。
`/v1/messages/count_tokens` に会話として渡した入力全体の数は使わない。

再計数はストリームの終了時刻を確定してから行うので、計数要求の時間は生成区間に含めない。
保存値と表示には `count_source=retokenized` を付け、生成時の内訳と区別する。
文字列の再トークン化は、生成時のトークン列と一致するとは限らない。
特殊トークンやブロック境界の扱いも異なるため、生成時の正確なトークン速度とは呼ばない。

非対応、404、タイムアウト、不正JSON、不正な数、モデル不一致などは理由付きの不明となる。
0や全体のusageで代用せず、元の要求の成否も変えない。片方だけ成功した場合、その値は残す。
実機の `/tokenize` 対応、応答形式、モデル識別子の整合は未確認である。
ローカルの偽サーバーによる要求形式・応答検証の成功は、実機対応を証明しない。

## 本文未到達なら合計の出力上限を調整する

`max_tokens` は思考と本文の合計の上限である。本文未到達の警告が出た場合は、既存の
`--set decode.max_tokens=N` で実行時に調整し、本文到達件数を再確認する。

```bash
# 2048 は指定例であり、本文到達を保証する値ではない
uv run bench run --target candidate-d --suite decode --profile probe --set decode.max_tokens=2048
```

既定の `probe`・`fast`・`quick`・`full` の上限と試行数、コード・散文・JSON × 英語・日本語の
6条件の生成指示は維持する。`thinking=server_default` も維持し、思考を無効化できるとは仮定しない。

## 保存済みの結果から比較する

再計数の有効・無効、方式、連結方法、特殊トークンの扱いはmanifestに記録する。
比較では同じ抽出経路を使い、方法や計数元が違う再計数指標は差・相対差・判定を出さない。
片側欠測なら既知側の値を示し、欠測や本文未到達の警告を残す。全出力指標の比較は維持する。

旧TrialRecord・manifest・summaryも読み込める。旧blocksから本文の存在が分かっても、
記録されていない段階別時刻や速度は補完しない。再計数設定の記録なしと、明示的な無効は区別する。
要約の再計算と比較は保存値だけで行い、不足した再計数値をサーバーへ問い合わせない。

公開する要約には数値・状態・計数方法・欠測理由だけを載せ、思考・本文・要求・ツール引数・
認証情報を含めない。本文を含む生データは引き続きgit対象外に置き、`publish` は
`summary.json` と `summary.md` の2ファイルだけを写す。
