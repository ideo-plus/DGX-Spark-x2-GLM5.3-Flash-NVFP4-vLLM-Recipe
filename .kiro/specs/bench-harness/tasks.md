# Implementation Plan

実装の順序は、土台 → 速さの計測 (P0 の終わりの条件はここまでで満たせる) → 品質の検査と長い会話の検査 → 統合と検証。`(P)` の付いたタスクは、書き込む範囲が重ならず、並行して進められる。

並行して進めるための決まり: 共有の型 (1.2)、設定の項目 (1.3)、試験用の偽のサーバー (1.4) は、土台のタスクで完結させる。タスク 2 以降は、これらのファイルを変更しない (例外は 8.4 だけ)。足りないものが見つかったら、並行のタスクの中で足さず、土台のタスクに戻して直す。`LICENSES.md` への行の追加は、1.1 (依存する部品) と 8.5 (課題とコンテナのイメージ) だけが行う。

- [ ] 1. 土台: 開発環境、共有の型、設定、試験用の偽のサーバー
- [x] 1.1 パッケージの骨組みと開発環境を用意する
  - `bench/` の下に Python のパッケージを作り、実行時の依存 5 つと開発時の依存を、版を固定して宣言する
  - 整形、静的検査、型の検査 (strict)、試験を、それぞれ 1 つのコマンドで流せるようにする
  - `.gitignore` に、仮想環境と、取得した課題の置き場所を足す
  - `LICENSES.md` を作り、依存する部品のそれぞれについて、名前、版、入手先、ライセンス、用途を書く
  - 完了の状態: 空のパッケージに対して、整形、静的検査、型の検査、試験がすべて通り、`bench --help` が使い方を表示する
  - _Requirements: 11.3_

- [x] 1.2 全体で共有する型を定義する
  - 対象サーバーの定義、計測の設定、計測ランの実行の条件と状態、1 つの要求の結果 (時刻、トークン数、中身、失敗)、条件の計画と飛ばした条件、試行のレコードと印、要約と比較の結果の型を定義する
  - 後続の部品が受け渡しに使う型も、ここで定義する: 記述統計と、割合と区間と、差の判定の型。内部の指標の論理名、読み取った値、導出値の型。ツールの定義、ツールの課題、分類の結果の型。探す課題、コードの課題、公開の課題の出どころ、採点の結果、隔離の実行の結果の型。後続のタスクは関数の実装だけを受け持ち、共有の型のファイルを変更しない
  - トークン数の型は、キャッシュの内訳の有無にかかわらず、入力の全長を返す
  - 要約の型は、送った内容と応答の本文を入れる項目を持たない
  - 完了の状態: すべての型が JSON に書き出せて読み戻せる。要約の型のスキーマに本文の項目がないこと、入力の全長の計算が内訳のある場合とない場合で正しいことを、試験が確かめる
  - _Requirements: 1.6, 3.2, 8.3_

- [x] 1.3 対象サーバーの定義と計測の設定を読み込めるようにする
  - 名前の付いた対象サーバーの定義を複数持てる設定ファイルと、`quick` と `full` の 2 つの計測の設定を用意する。比較の基準の対象サーバーを最初から入れておく
  - 認証の情報は環境変数の名前だけを設定に書き、値は実行時に読んで、書き出しでは伏せる
  - 生データの置き場所が git の管理の対象でないことを確かめ、対象なら読み込みを失敗させる
  - 試行の回数 (生成速度は 10 以上) と慣らしの回数、出力の上限、サンプリングの設定、同時の本数、長い会話の段階の刻みと試行の数と会話の本数、長さの許容の幅、比較の許容の幅、崩れのしきい値、成功した試行の最小の数、続けて失敗してよい回数を、設定で変えられるようにする
  - 後続の部品が使う項目も、ここで入れる: 内容の種類ごとの 1 トークンあたりの文字数、3 種類の制限時間 (最初のイベントまで、イベントの間隔、全体)、内部の指標を読む間隔、出力が壊れている疑いの判定の長さと回数、コードの隔離の実行環境の選択とイメージのダイジェスト、乱数の種。設定の項目を足す変更は、このタスクで完結させる
  - 完了の状態: 知らない対象サーバーの名前と、下限を割った値が、項目の名前つきのエラーになる。認証の情報の値が、書き出した JSON に現れない。管理の対象の場所を生データの置き場所に指定すると失敗する
  - _Requirements: 1.1, 1.8, 2.2, 4.1, 6.8, 8.5_

- [x] 1.4 試験用の偽のサーバーを作る
  - `/v1/messages` のストリーム、`/v1/models`、`/version`、`/metrics` に応答する、試験専用のサーバーを作る
  - 試験ごとに、イベントの列と順序、イベントの間の遅れ、トークン数 (キャッシュの内訳の有無)、`ping` や知らないイベントの混入、HTTP のエラー、ストリームの途中のエラー、応答の停止を指定できるようにする
  - 後続のタスクが要る振る舞いも、ここで入れる: 入力の長さの上限の申告と、上限を超えた要求への HTTP 400。終わり方 (`stop_reason`) の指定。同時に届いた要求の本数と時刻の記録。ツール呼び出しのブロック、記法が本文に漏れた応答、壊れた引数の応答。送られた入力の大きさに応じた入力のトークン数の返却。トークンを数える口 (ある場合とない場合)。要求の本文の記録 (試験から読み出せる)
  - タスク 2 以降は、偽のサーバーを変更しない
  - 完了の状態: 指定した遅れとイベントの列が、実際のソケット越しにそのとおり届くことを、偽のサーバー自身の試験が確かめる
  - _Requirements: 2.3, 10.1_

- [ ] 2. 計測と分析の部品
- [x] 2.1 (P) 1 つの要求を送って、時刻と中身を返すクライアントを作る
  - `/v1/messages` にストリームで要求を送り、イベントを受け取った直後に時刻を打ち、送り始め、最初のトークン、最初の本文、最後のトークン、終わりの時刻を返す
  - トークン数は、終わりの側のイベントの値を正とし、来なかったときだけ始まりの側の値を使う
  - 本文、thinking、ツール呼び出し (引数は、解析する前の文字列と、解析できたときの値) をブロックとして返す
  - 通信の失敗、HTTP のエラー、ストリームの途中のエラー、3 種類の時間切れ (最初のイベントまで、イベントの間隔、全体) を、例外ではなく結果の値として返す。やり直しはしない
  - 認証の情報は 2 種類のヘッダーに付け、結果には含めない。知らないイベントと項目は無視する
  - 完了の状態: 偽のサーバーに対して、最初のトークンまでの時間と生成速度が、期待の値の ±5% に入る。イベントの順序の入れ替え、`ping` の有無、知らないイベントの混入で、同じ結果になる。イベントの間隔の時間切れが、失敗の値として返る
  - _Requirements: 1.8, 2.3, 3.2, 4.3, 6.7, 10.1, 10.6_
  - _Boundary: client/messages_

- [x] 2.2 (P) 対象サーバーの内部の指標を読んで、増分と導出値を出す
  - `/metrics` のテキストを取得して解析し、加工する前の形と、論理名ごとの値と、見つからなかった名前を返す
  - 2 つの時点の値から、投機的デコードの当たり率、平均の受理長、生成のステップの数、1 ステップあたりのトークン、プレフィックスキャッシュの効いた割合、追い出しの回数を出す。分母が 0 のときは値なしにする
  - 計測の間に一定の間隔で読み、KV の使用率の最大を返す
  - 名前の対応は vLLM の V1 のものを既定とし、対象サーバーの定義で上書きできるようにする。値の型は 1.2 のものを使う
  - 完了の状態: vLLM の形式の例から導出値が出る。投機的デコードの指標がない例と、`/metrics` が 404 の場合で、例外にならず、得られなかった名前が返る
  - _Requirements: 7.1, 7.2, 7.3, 7.4_
  - _Boundary: metrics/scrape_

- [x] 2.3 (P) 生データを保存して読み戻す仕組みを作る
  - 計測ランごとに、重ならない識別子のディレクトリを作り、実行の条件と状態、試行のレコード、送った要求の本文、加工する前の内部の指標と導出値を保存する
  - 試行のレコードは 1 行ずつ書き足し、書くたびにディスクに同期する。要求の本文は圧縮し、内容のハッシュで重複を除く
  - 状態の書き換えは、別名で書いてから置き換える。最後の行が途中で切れているレコードのファイルは、その行だけを捨てて読む
  - 完了の状態: 書いている途中でプロセスを止めても、それまでの試行が読み戻せる。同じ本文を 2 回保存してもファイルは 1 つ。保存したどのファイルにも認証の情報の値が現れない
  - _Requirements: 1.5, 1.6, 7.5, 8.1, 8.5, 8.7_
  - _Boundary: store/rawstore_

- [x] 2.4 (P) 統計の関数を作る
  - 連続の値について、サンプル数、平均、中央値、最小、最大、標準偏差、四分位範囲、変動係数を出す
  - 割合について、分子と分母、正確な二項の区間 (両側 95%)、片側 95% の上限を出し、しきい値を下回った、上回った、試行の数が足りない、のどれかを判定する。崩れが 0 件のときに要る試行の数を返す
  - 2 組の連続の値の差について、対応のある場合とない場合の再標本化で、ばらつきの範囲に収まるかを判定する。乱数の種は固定する
  - 2 つの割合について、区間が重なるかどうかで、差が意味のあるものかを判定する。結果の型は 1.2 のものを使う
  - 完了の状態: 崩れ 0 件で 299 回なら 1% を下回り、298 回なら下回らない。同じ分布の 2 組が「収まる」、10% ずらした 2 組が「収まらない」になり、種が同じなら結果が同じになる
  - _Requirements: 2.4, 3.7, 5.6, 6.5, 9.2, 9.6_
  - _Boundary: analysis/stats_

- [x] 2.5 (P) 種から決まる合成の文章を生成する
  - 型紙に値を埋める方法で、散文 (英語、日本語)、コード、ログの 4 種類の文章を、狙ったトークン数に相当する文字数で生成する。比 (1 トークンあたりの文字数) は設定から受け取る
  - 入力の先頭に入れる、決まった長さの識別子を生成する。キャッシュが効かない条件では試行ごとに違い、効く条件では同じになるようにする
  - 時刻、環境、辞書の順序に依存しない
  - 完了の状態: 同じ種と引数で 2 回生成して、バイト単位で同じになる。効かない条件の識別子が試行ごとに違い、効く条件の識別子が同じになる。生成した文章に、業務の実データに由来する内容がない (すべて型紙と乱数から作る)
  - _Requirements: 2.1, 3.4, 11.1, 11.4_
  - _Boundary: corpus/synth_

- [x] 2.6 (P) 出力が壊れている疑いを見つける
  - 応答の本文 (thinking を含む) に、置き換え文字があるか、決まった長さ以上の同じ並びが、決まった回数以上、間を空けずに続いているかを判定する。長さと回数は設定から受け取る
  - 完了の状態: 置き換え文字を 1 つ含む本文と、同じ 12 文字の並びが 8 回続く本文に、それぞれの印が付く。7 回では付かない。ふつうの散文とコードの例には、どちらも付かない
  - _Requirements: 10.7_
  - _Boundary: scoring/sanity_

- [x] 2.7 計測の前提を確かめる
  - 対象サーバーに短い要求を 1 回送り、応答とトークン数があることを確かめる。満たされていない前提 (接続できない、HTTP のエラー、トークン数がない、出力がない) を、値として返す
  - 対象サーバーが返すモデルの名前、版、入力の長さの上限 (得られなければ対象サーバーの定義の値、それもなければ不明)、始める前の実行中の要求の数を得る。これらが得られなくても、前提の不足にはしない
  - 与えた文章のトークン数を、トークンを数える口で得る。その口がない対象サーバーでは、出力 1 トークンの要求を送って、返ってきた入力のトークン数で代える
  - 完了の状態: トークン数を返さない偽のサーバーに対して、理由が「トークン数がない」になる。上限を返す偽のサーバーと返さない偽のサーバーで、上限の決まり方が設計のとおりになる。トークンを数える口がある場合とない場合で、同じ文章に同じトークン数が返る
  - _Depends: 2.1_
  - _Requirements: 1.3, 1.4, 3.6, 6.9_

- [ ] 3. 速さの計測と、計測ランの進行
- [x] 3.1 測る項目のまとまりに共通の約束事を作る
  - 条件の鍵、主な結果と参考の区別、試行の回数と慣らしの回数、サンプリングの設定、出力の上限、同時の本数を持つ、条件の計画の形を決める
  - 上限より長い条件を、送る前に飛ばす。上限が不明で、対象サーバーが上限の超過を返したときは、その条件を飛ばして理由を残す
  - すべての試行に共通の印 (狙った長さからの外れ、出力のトークンが少なすぎる、出力が壊れている疑い) を付ける
  - 同じ条件のすべての試行が、同じサンプリングの設定と出力の上限を使うことを保証する
  - 完了の状態: 上限が 3 万 2 千の偽のサーバーに対して、12 万 8 千の条件が飛ばされ、理由が残る。狙った長さから許容の幅を超えて外れた試行に印が付く
  - _Depends: 2.1, 2.6, 2.7_

- [x] 3.2 (P) 生成速度のまとまりを作る
  - コードと散文、英語と日本語の 4 つの条件で、試行ごとに違う、長く書かせる指示を送る。同じ番号の試行は、必ず同じ指示になる
  - 慣らしの試行を先に行い、集計と分けて記録する。出力の上限に届かずに終わった試行に印を付ける
  - 完了の状態: 偽のサーバーに対して 4 つの条件が実行され、慣らしと本番の試行が分かれて記録される。上限に届かない応答を返す偽のサーバーで、印が付く
  - _Depends: 2.5, 3.1_
  - _Requirements: 2.1, 2.2, 2.5, 2.6, 2.7_
  - _Boundary: suites/decode_

- [x] 3.3 (P) 入力の処理と最初のトークンまでの時間のまとまりを作る
  - およそ 8k、32k、128k トークンの入力で、キャッシュが効かない条件 (試行ごとに違う識別子) と、効く条件 (同じ識別子と前置きで、末尾の問いだけを変える) を、別の条件として測る。出力の上限は小さくする
  - 効く条件の 1 回目は、キャッシュを温める慣らしとして扱う
  - 完了の状態: 効かない条件で送った入力の先頭が、試行の間でも、ほかの条件との間でも重ならない。効く条件の入力は先頭が同じで、末尾だけが違う
  - _Depends: 2.5, 3.1_
  - _Requirements: 3.1, 3.2, 3.4, 3.5, 3.6_

- [x] 3.4 (P) 同時処理のまとまりを作る
  - 同時の本数 1、2、4、8 のうち、選ばれたものについて、1 回ぶんの要求を合図で同時に送り始め、実際に送り始めた時刻を要求ごとに記録する。入力は 1 本ごとに違い、先頭も重ならない
  - 1 本と 2 本を主な結果、4 本と 8 本を参考として、条件に印を付ける
  - 完了の状態: 偽のサーバーに対して同時 4 本で、送り始めの時刻の幅が 50 ミリ秒以内になる。1 本が失敗しても、残りのレコードが残る

  - _Requirements: 4.1, 4.3, 4.4_
  - _Boundary: suites/concurrency_

- [x] 3.5 計測ランを始めから終わりまで進める
  - 前提を確かめ、満たされていれば、実行の条件 (対象サーバーの定義、対象サーバーが返したモデルの名前と版、日時、まとまり、解決済みの設定、入力の長さの上限、道具の版、生成器の版) を組み立てて計測ランを作る。道具の版は、パッケージの版、git のコミット、未コミットの変更の有無から作る
  - 選ばれたまとまりを順に実行し、試行が 1 つ終わるたびにレコードを書く
  - 条件ごとの前後で内部の指標を読み、その間は定期的に読んで、加工する前の形と導出値を保存する。始める前に実行中の要求があれば、警告を記録する
  - 要求の失敗が決まった回数続いたら、状態を「停止」にして止める。上限の超過は数えない。中断の合図を受けたら、送っている途中の要求を打ち切り、状態を「中断」にして終わる
  - 標準エラーに、まとまり、条件、終わった試行の数と全体の数、失敗の数を出す
  - 完了の状態: 偽のサーバーを試行の途中で止めると、それまでの試行が残り、状態が「停止」になる。中断の合図で「中断」になる。前提が満たされないときは、計測ランのディレクトリが作られない
  - _Depends: 2.2, 2.3, 2.7, 3.1_
  - _Requirements: 1.2, 1.3, 1.6, 1.7, 7.1, 10.3, 10.4_

- [ ] 4. 要約、比較、公開
- [x] 4.1 (P) 生データから、速さの要約を作る

  - 条件ごとに、失敗の件数と、印の件数 (早く終わった、長さが外れた、出力が壊れている疑い) を示す。成功した試行が最小の数に届かない条件と、一部が失敗した同時処理の条件に、印を付ける
  - 要約の先頭に実行の条件を置き、未完了の計測ランにはその旨を示す。内部の指標の導出値を、条件ごとに載せる
  - 人が読む要約と、道具が読む要約の 2 つを、計測ランのディレクトリに書く。何度実行しても同じ結果になる
  - 完了の状態: 用意した生データの例から、2 つの要約ができる。どちらにも、送った内容と応答の本文の目印の文字列が含まれない。主な結果と参考が分かれて表示される
  - _Depends: 2.3, 2.4_

## Implementation Notes

- 1.1: 検証の基準のコマンドは、`bench/` で `uv sync`、`uv run ruff check .`、`uv run ruff format --check .`、`uv run mypy`、`uv run pytest -q`、`uv run bench --help`。`uv` が選ぶ Python は 3.13 (`requires-python >= 3.12`)。ビルドのバックエンドは hatchling
- 1.2: 共有の型はすべて凍結 (frozen) で、知らない項目を拒否する。更新は `model_copy(update=...)` で行うが、これは検証を通らない。値を上書きしたあと (5.1 の試行の回数の上書き、3.5 の実行の条件の更新) は、`model_validate(x.model_dump())` で検証し直すこと
- 1.2: list や dict の項目を持つ凍結の型 (`ToolDef`、`ToolTask`、`ConditionPlan`、`TrialRecord` など) は `hash()` で落ちる。set に入れたり、dict の鍵にしたりしない
- 1.2: `MessagesRequest.extra` は入れ子の写像で、送るときに本文の最上位へ混ぜるのはクライアント (2.1) の仕事。保存する本文 (2.3) は、混ぜたあとの、実際に送った形にする
- 1.2: 条件ごとの内部の指標の増分 (`metrics/deltas.jsonl`) の行の型は、共有の型にない。保存の部品 (2.3) が行の型と読み戻す関数を出し、分析 (4.1) はそれを読む (分析 → 保存の読み取りは、依存の向きで許されている)
- 1.2: 「採点できなかった件数」(5.7) の受け皿は `MetricResult.flag_counts`。鍵の名前は 4.2 で `not_scored` に固定する
- 1.3: 設定の上書きの鍵は、点でつないだ経路 (例: `decode.trials`)。`config.apply_overrides` が上書きのあとに検証し直す。5.1 と 3.5 はこれを使い、別の形式を作らない
- 1.3: 設定ファイルの場所は、`config.py` からの相対 (`bench/config/`)。ソースの木か editable の導入でだけ動く (この道具は `bench/` で `uv run` する前提)
- 1.3: 安全に関わる確認 (生データの置き場所など) は、外部のコマンドの失敗を「問題なし」と見なさない。確かめられた場合だけを許可にし、わからない失敗はエラーにする。レビューでは、偽の実行ファイルを PATH に置いて失敗を再現する手が有効だった
- 1.4: 偽のサーバーは `bench/tests/fake_server.py` (標準ライブラリだけ)。試験からは `import fake_server` と、fixture の `fake_server` / `fake_server_factory` で使う。使い方は、先頭の docstring が唯一の契約書。タスク 2 以降は、このファイルと `conftest.py` を変更しない
- 1.4: 時刻を判定する試験の決まり。(1) 下限 (早すぎない) を 1 回の測定で判定してよいのは、基準点が「試験自身が要求を送る前に打った時刻」のときだけ。2 つのイベントの読み取り時刻の差は、前の読み取りが遅れると縮むので、下限に使わない。(2) 遅い側は、個々の値を狭い幅で全数判定しない。中央値、全体の幅、外れの本数の上限で見る。(3) 測る前に 1 回流して、接続を温める。(4) 時刻に関わる試験を足したら、そのファイルを 25 回以上続けて流して、失敗 0 を確かめる (5 回では、1 割の揺らぎを半分の確率で見逃す)
- 1.4: この Mac は、ふだんからロードアベレージが 10 前後ある。揺らぎの確認のために、負荷のプロセスを起動しない (回収が漏れると、測定が壊れる)

- 2.4: 再標本化の判定は、試行 10 回の対応ありで、許容の幅が 0 のとき、同じ分布の 2 組を約 8% の確率で「収まらない」と誤る (名目は 5%)。既定の許容 2% があれば、測り方のばらつき (変動係数) が 1% なら 0%、2% なら 1 条件あたり約 1.5%、3% を超えると 20 条件で 1 件以上の偽の「収まらない」が出る確率が 5 割を超える。8.2 で収まらない条件が出たら、まず試行の回数を 20 回以上に増やして測り直すこと

- 2.6: 出力の健全性の検査は `bench_harness.scoring` の `detect_output_anomalies(text, repeat_min_chars, repeat_min_count)`。渡す本文は `collect_text(result)` (本文と thinking)。ツールの引数は `collect_tool_input_text(result)` で取り出し、置き換え文字の検査にだけ使う (JSON は構造が繰り返すので、繰り返しの検査にはかけない)。まとまりの共通の処理 (3.1) は、この 2 つを呼んで印を付ける
- 2.6: 繰り返しの検出は、定義 (`unit * 回数` を含む。`unit` は `repeat_min_chars` 文字以上) と厳密に一致する。単位の長さの上限は 4096 文字。印を付けないのは、単位の空白でない文字が 0 種類、または英数字でない 1 種類だけのとき。同じ英数字の連続 (`aaaa…`、`的的的…`) には印を付ける。2 種類の記号が混ざる広い表の区切り行 (`|---` が 25 列以上) と、`0,0,0,…` のような CSV には、定義どおり印が付く (印の付いた試行は集計から外さず、件数を示すだけ)。使い方の文書 (8.5) に書くこと

- 2.7: トークン数の計数は `count_input_tokens(client, target, request, …) -> TokenCount` (`tokens` と、どちらの方法で数えたかの `method`)。数える口に送る本文は、公式の項目 (`model`、`messages`、`system`、`tools` など) と、トークン数に効きうる `extra` だけ。口が「ない」と見なすのは 404 / 405 / 501 だけで、それ以外の失敗は `ProbeError`。比の測定のコマンド (5.1) は、これを呼んで表示するだけ

- 3.1: まとまりの共通の部品は `bench_harness.suites.base`。まとまりは薄く書く: `plan(ctx)` では `plan_condition(...)` (上限に収まらなければ `SkippedCondition` が返る) だけで計画を作り、`run_condition(ctx, cond)` では `iter_trials(cond)` で `(試行の番号, 慣らしか)` を回し、入力を作って `run_trial(ctx, cond, trial_index=…, warmup=…, system=…, messages=…, …)` を呼び、返ったレコードを `yield` し、その直後に `abort_if_context_limit(cond, record)` を呼ぶ (上限の超過なら `ConditionAborted` が飛ぶ)。要求の組み立て、本文の保存、共通の印、判定の付加 (`verdict=`) は、`run_trial` が受け持つ。まとまりは `suites/base.py` を変更しない
- 3.1: `run_trial` の引数。生成速度を測る試行は `measures_decode_speed=True` (出力が 16 トークン未満なら印)、出力の上限まで書かせる試行は `expect_full_output=True` (上限に届かずに終われば印)。同時処理は `round_id`、`stream_index`、`start_gate` (本文を保存したあと、送る直前に待つ合図。送信の時刻は、合図のあとに打たれる)。サーバーごとの追加の項目は `extra=` (型のある項目と重なると `ValueError`)。同じ条件の試行が同じ設定になるのは、計画を `plan_condition` で 1 つだけ作って使う限りで保証される
- 3.1: 番号と種。慣らしと本番は、それぞれ 0 から番号を振る (`(条件, warmup, 番号)` で一意)。試行ごとの種は `trial_seed(profile.seed, cond.key, trial_index, warmup=…, stream_index=…)` (`run_id` を含まないので、本番の i 番目は、計測ランをまたいで同じ入力になる)。先頭の識別子は `cold_prefix_nonce(...)` (`run_id` を含む) と `warm_prefix_nonce(...)`、先頭の行つきのシステムプロンプトは `system_with_prefix(...)`。接続を温める慣らしの既定の回数は `DEFAULT_CONNECTION_WARMUP_TRIALS`
- 3.1: 計測ランの進行 (3.5) への申し送り。`make_suite_context(...)` は、設定の thinking が `server_default` でないと `ValueError` を投げる (渡し方は 8.4 で決まる)。計測ランのディレクトリを作る前に文脈を組み立て、投げられたら前提の不足として終了の値 1 にする。`ConditionAborted` は捕まえて、`skipped` を実行の条件に足し、連続の失敗には数えず、次の条件に進む。`put_body` が投げた例外 (保存の失敗) は、握りつぶさずに計測ランを止める
- 3.1: 条件の鍵の長さの表記 `tokens_label(20000)` は `20k` (0 で埋めない)。長い会話の段階 (7.2) の鍵を設計どおり `agent/stage/020k` にするなら、7.2 の側で組み立てる
- 3.2: 生成速度のまとまりは `bench_harness.suites.decode` の `DecodeSuite` (計測ランの進行は、モジュールを直接読み込む)。題材は試行の番号だけで決まり (8 × 4 = 32 通り。設定の種では変わらない)、文中の架空の管理番号だけが種から決まる。求める量は、出力の上限を大きく超えるようにしてある (コードは 150 行、英語は 1200 語、日本語は 3000 字)。出力の上限を 1024 より大きくするなら、この量も見直すこと
- 3.3: 入力の処理のまとまりは `bench_harness.suites.prefill` の `PrefillSuite`。文書は長さごとに 1 つで、効く条件と効かない条件、すべての試行、計測ランをまたいで同じ (違うのは、先頭の行と末尾の問いだけ)。文書はコード、ログ、英語の散文を 3 等分で混ぜる。効かない条件の慣らしは、接続を温めるだけの短い文書 (約 300 トークン) で、長さの外れの印が付く (慣らしは集計に入らない)。効く条件は、1 回目の要求がキャッシュを温める慣らしになる
- 3.3: 上限の判定は「入力の狙い + 出力の上限 ≤ 上限」。上限がちょうど 32000 のサーバーでは、32k の条件 (32000 + 16) も飛ばされる。上限が 32768 や 131072 のサーバーなら、32k と 128k は収まる
- 3.4: 同時処理のまとまりは `bench_harness.suites.concurrency` の `ConcurrencySuite`。1 つの試行 = 1 回ぶん (n 本)。レコードは `(condition, warmup, trial_index = round_id, stream_index)` で一意で、1 回ぶんの n 本を、ストリームの番号の順に返す。1 本が失敗しても n 本のレコードが残る。慣らしは 1 回ぶん (n 本の接続を開く)。分析 (4.1) は、`(condition, warmup, round_id)` でまとめて、1 本あたりの速さ、1 回ぶんの合計 (出力のトークンの合計 ÷ (最後のトークンの時刻の最大 − 最初のトークンの時刻の最小))、1 本ごとの最初のトークンまでの時間を出す
- 3.4: 仕掛け (合図、読み飛ばし、キャッシュ、再試行の抑止など) を確かめる試験は、その仕掛けがないと結果が変わる状況を、わざと作ること。同時に送り始める合図は、保存が速いと、合図がなくても揃ってしまう。1 本だけ保存を 200 ms 遅らせて、初めて違いが出た。「うまくいく入力」だけの試験では、仕掛けを丸ごと外しても通る (2.6 の区間の読み飛ばしも、同じ形の穴だった)
- 3.5: 計測ランの進行は `bench_harness.runner` の `async execute_run(req, progress, *, targets_path=…, profiles_path=…, results_root=…, registry=…, env=…, clock=…) -> RunOutcome`。進み具合は `ProgressSink` (標準エラーに出す実装は `StderrProgressSink`。標準出力には何も出さない)。まとまりの対応表は `default_suite_registry()` で、まとまりを足すのは 1 行 (8.1)。同じまとまりを 2 回選ぶと、設定の誤りになる
- 3.5: コマンドの入口 (5.1) の決まり。`asyncio.run(execute_run(...))` を呼ぶ。計測ランのディレクトリを作る前の失敗は `PreconditionError` (`exit_code = 1`、理由は日本語) が投げられるので、標準エラーに出して 1 で終わる。`RunOutcome.exit_code` は 0 / 2 / 130。ディレクトリができる前の `KeyboardInterrupt` は 130 に、外に出た `StoreError` / `OSError` は 2 に直す。要約は、計測のあとに入口が作る (`RunOutcome.run_dir`)。終了の値の定数は `EXIT_OK` / `EXIT_PRECONDITION` / `EXIT_ABORTED` / `EXIT_INTERRUPTED`
- 3.5: 連続の失敗は、レコードごとに数える (同時処理の 1 回ぶんの n 本が全滅すれば n 回。既定の 5 回と c8 なら、1 回ぶんの全滅で止まる)。止めると決まっても、すでに応答を得た要求のレコードは書き切る。まとまり (6.7、7.2) は、後始末で `CancelledError` を握りつぶさないこと (2 回目の SIGINT が効かなくなる)
