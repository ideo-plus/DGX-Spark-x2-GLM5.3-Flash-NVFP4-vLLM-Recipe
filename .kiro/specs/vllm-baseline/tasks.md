# Implementation Plan

この計画は、3 つの部分からなる。

- **1〜5 は、Spark なしで、Mac の上だけで進める** (道具の実装と試験)
- **6 は、構成の値と、手順と記録の書式を用意する** (Spark に触らない)
- **7〜8 は、実機で行う**。Spark の状態を変える操作 (配布、イメージの取得、重みの取得、起動、停止、確認のコンテナの起動) の前に、毎回、計測者の了承を取る。計測者が別に起動していた構成 (`exl3-tp2`) の中身は、見ない。8 は、7.2 (段 0) の結果で分かれる。打ち切りになった場合は、8.1〜8.7 を行わず、8.8 だけを、計測者が改めた終わりの条件のもとで行う

- [x] 1. 土台: プロジェクトの骨組み、共有の型、構成の読み込み、遠隔の実行、試験用の偽物
- [x] 1.1 `serving/` のプロジェクトの骨組みを作る
  - `bench/` と同じ形 (src レイアウト、uv、`uv.lock` のコミット、ruff、mypy strict、pytest) で、`serve` コマンドが入口だけ動くようにする
  - 記録の置き場所と、仮想環境やキャッシュを、git の管理の対象から外す
  - 足した依存を、版とライセンスとともに `LICENSES.md` に書く。使わないと決めたもの (ansible、paramiko) と理由も書く
  - 完了の状態: `serving/` で `uv sync` のあと、`uv run serve --help` と `uv run serve --version` が 0 で終わり、疎通の試験、ruff、mypy が通る
  - _Requirements: 3.8, 3.9, 7.8_
- [x] 1.2 共有の型を定義する
  - 設定 1 つ (フラグ、値、理由、根拠、値が待ち受けのポートかどうかの印。フラグを持たない位置の引数も表せる)、イメージの参照、重みの参照、重みのマニフェスト、照合の結果の記録、構成、ノード、了承を得た計画、コマンドの結果、関門の結果、組み立てたコンテナの計画、起動の記録、起動と通信の観察の結果、知っている失敗の種類、ノードとサービスの状態、起動・停止・短い要求・縮小の確認の結果、リンクの報告、帯域と A/B の結果、見張りの観察と判定、thinking の確かめの結果の型を、書いたあとに変えられず、知らない項目を断る型として定義する
  - 構成の種類は 5 つ (推論サーバー、縮小の確認、通信の確認のジョブ、重みの取得、イメージの中の読み取り)。構成は、イメージの参照のあとに続く引数を、書いた順を保つ 1 つのまとまりとして持ち、コンテナの中で動かすプログラムは、専用の項目ではなく、docker の設定として表す。名乗るモデルの名前は、推論サーバーと縮小の確認でだけ必須で、ほかでは持たない
  - 根拠は、「出典と原文の組」か「実測の記録の場所」の、どちらか一方だけを受ける
  - この部品は、ほかの `serving_kit` の部品を読み込まない。設計が挙げる型は、すべてここに置く。あとの並行のタスク (2.1〜2.4、4.1、4.3、4.5、4.6) は、この部品を書き換えない。型の不足が見つかったら、並行の作業を止めて、この部品の変更を 1 つの作業として先に行う
  - 完了の状態: 型の試験で、根拠が両方ある、どちらもない、出典だけで原文がない、のそれぞれが断られる
  - _Requirements: 3.1, 3.4, 3.6_
- [x] 1.3 構成とノードの定義を読み込み、検査する
  - TOML を読み、誤りを 1 つの種類にまとめ、項目の名前つきの日本語の文で、すべて並べて示す
  - 検査: 根拠 (実測の記録のファイルが実在すること)、イメージの参照がダイジェストの形、重みの版が 40 桁、モデルの名前が 1 つで `/` を含まない、投機的デコードの指定がない、置き換えの印が決めたものだけ、禁じる docker のフラグ (特権、プロセスやユーザーの名前空間の共有、セキュリティの指定の上書き、`-v`、自動の起こし直し、終了時の自動の削除) がない、`--mount` の元が Spark の置き場所の下だけ、`--device` と `--cap-add` が名前の一覧 (`/dev/infiniband`、`SYS_NICE`、`IPC_LOCK`) にあるものだけ (根拠があっても、一覧にないものは断る)
  - 直結の値の検査だけは、構成を選んだときに、選んだ構成について行う。この検査が掛かるのは、推論サーバーと通信の確認のジョブの、2 台の構成だけで、重みの取得、イメージの中の読み取り、縮小の確認には掛からない (取得と読み取りは、直結の値を実測する前に流すため)
  - 名前のない構成を選ぶと、使える名前を添えて断る
  - 完了の状態: 根拠のない設定を 2 つ含む構成が、2 つの項目の名前を並べて断られる。直結の値が空でも、縮小の確認と取得の構成は選べて、推論サーバーの 2 台の構成は選べない
  - _Requirements: 3.1, 3.6, 3.7, 4.7, 6.2, 6.7, 11.5_
- [x] 1.4 遠隔の実行の部品と、試験用の偽の実行役を作る
  - ssh と rsync を、引数のリストで呼ぶ。遠隔のシェルに渡る文字列は、引用の事故が起きない方法で作る。非対話の指定と、接続の時間切れを付ける
  - 実行できるコマンドを、許可の一覧で絞る (`sudo`、`apt`、`pip`、`systemctl` は呼べない)。`docker` は、サブコマンドも許可の一覧で絞る (`exec`、`build`、`rmi`、`system` などは呼べない)
  - 状態を変える呼び出しは、了承を得た計画に含まれていなければ、実行せずに誤りにする。計画は、前に進むコマンドと、それを巻き戻すコマンドの組で持ち、巻き戻しのコマンドは、前に進むコマンドが途中で失敗したあとでも実行できる
  - 配布は、つねに状態を変える呼び出しとして扱い、了承を得た計画に含まれていなければ誤りにする。配布の宛先は、Spark の置き場所の下の、決まった部分 (配るスクリプトと、記録) だけ。重み、キャッシュ、コンテナの記録の置き場所は、配布の宛先にできない。回収の宛先は、Mac の記録の置き場所の下だけ
  - 偽の実行役は、呼ばれた引数の列と順序を記録し、台本どおりの結果を返す
  - 完了の状態: 空白と引用符を含む引数が 1 つの引数のまま渡る、許可の一覧にないコマンドと docker のサブコマンドが断られる、了承のない状態の変更が誤りになる、了承した計画の巻き戻しが失敗のあとでも実行できる、の 4 つの試験が通る
  - _Requirements: 1.2, 1.5, 2.1, 2.3, 2.7, 8.6_
- [x] 1.5 試験用の偽の推論サーバーを作る
  - 標準ライブラリだけで、`/health`、`/v1/models`、`/metrics`、`/version`、`/v1/messages` に応える。HTTP のモックのライブラリは使わない
  - 応答を台本で切り替えられる (何回目から 200 を返すか、応答の確認がいつから失敗するか、生成のトークンの数がいつ止まるか、投機的デコードの指標を出すか、`/v1/messages` の応答の thinking のブロックの長さ、本文、トークンの数、終わりの理由)。受け取った要求の本文を記録して、試験から読める。あとの並行のタスク (4.1、4.5、4.6) は、この偽物を書き換えずに、台本だけで使う
  - 完了の状態: 試験の中で、空きポートに立ち、台本どおりに応え、終わると止まる
  - _Requirements: 1.4, 7.7_
- [x] 1.6 2 台の Spark から、読み取りのコマンドの実物の出力を採って、試験の見本にする
  - 読み取りだけを行う (状態を変えない。CLAUDE.md が認める、ssh での確認の範囲)。採るもの: docker の版、自分のラベルで絞ったコンテナの一覧 (JSON の形。この時点では空)、GPU を使っているプロセスの問い合わせ、GPU の使用率の問い合わせ、ディスクの空き、インターフェースの一覧とアドレス、インターフェースの速さ、待ち受けているポートの一覧、ホストの名前
  - コンテナの一覧は、最初から、自分のラベルで絞って採る。絞らない一覧には、ラベルのないコンテナのイメージとコマンドが入るので、採らない、見ない (別の構成の中身を読まない)。ラベルのないコンテナに、どの操作も向けない
  - GB10 のユニファイドメモリのために `[N/A]` になる列があれば、その旨を見本に注記する
  - 自分のコンテナがあるときの出力と、イメージを取得したあとのダイジェストの一覧は、ここでは採れない (7.1 と 7.2 で採って、見本を足す)
  - 完了の状態: 2 台ぶんの見本が、試験の見本の置き場所にコミットされ、どの見本にも、別の構成の中身、アドレス以外の個人の情報、認証の情報が含まれていない
  - _Requirements: 1.6, 2.2, 2.4, 4.1_

- [x] 2. 中核の部品
- [x] 2.1 (P) 構成から、コンテナの起動の引数の列を組み立てる
  - 入出力のない関数として、構成とノードから、head と worker のそれぞれの引数の列、コンテナの名前、共通の 7 つのラベル (重みの参照を持つ構成は、重みのラベルが付いて 8 つ。通信の確認の A/B の回は、さらに腕と回のラベルが付く) を作る。この道具が起こすコンテナは、5 つの種類のどれも、すべてここを通す。どれも切り離して起こし、前面で動かす指定と、終了時に自動で消す指定は使わない
  - ラベルの 1 つは、2 台ぶんの、組み立てた引数の列 (置き換えの印を埋めたあと) から、ラベルの引数を除いたものの sha256 にする。説明、理由、根拠、待ちの上限を変えても変わらず、コンテナの中身に効く変更 (フラグ、値、イメージ、重み、ノードの値) だけで変わる
  - 道具が必ず付ける引数 (切り離して動かす、取得しない、名前、ラベル、自動で起こし直さない) にも、構成と同じ形の根拠を持たせる
  - 環境変数は、構成に書いたものだけを渡す。Mac の側の環境を引き継がない。秘密らしい名前の変数を断る
  - 完了の状態: 見本の構成から作った 2 台ぶんの引数の列が、固定した列と一致する。2 台の差が、順位、API を持たない指定、自分のアドレス、置き換えの印だけである。イメージの参照のあとの引数が、書いた順に並び、フラグを持たない設定が位置の引数になる。説明と理由だけを変えても、sha256 のラベルが変わらない。Mac の側に置いたトークンの変数が、どの引数にも現れない。イメージをビルドする列を作る経路がない
  - _Requirements: 1.3, 2.6, 3.10, 6.1, 8.6_
  - _Boundary: plan_
- [x] 2.2 (P) 起動の記録と、通信の記録から、事実を読み取る
  - 起動の記録から、版、アテンションに選ばれた部品と候補、エキスパートに選ばれた部品、KV キャッシュの大きさ、ロードと起動の所要、投機的デコードの設定の有無を読む
  - 知っている失敗 (アテンションの形の assert、部品の全滅、対応するカーネルがない、ブロックの大きさ、起動時のメモリの検査、DeepGEMM がない) を見分け、誤りの前後の行を抜き出す
  - 通信の記録から、版、使われた経路、デバイスが見つからなかったか、束ねられたか、チャンネルの数、GPUDirect の有無を読む
  - 読めなかった項目は、断らずに、空のまま返す
  - 完了の状態: それぞれの文字列を含む見本の記録から、期待した値が読める。どれも含まない記録は、すべて空で返る
  - _Requirements: 4.4, 5.2, 5.3, 6.3_
  - _Boundary: observe_
- [x] 2.3 (P) 起動の前の関門と、了承の仕組みを作る
  - 読み取りだけで判定する関門を、この順に流す: 入れるか、自分のコンテナが動いていないか、GPU を使っているプロセスがないか、構成が結び付ける置き場所が 2 台にあるか、イメージのダイジェストが合うか、重みの照合の記録と一覧と大きさが合うか、ディスクの空きが足りるか、構成が使う待ち受けのポートが空いているか
  - 同時に動かす自分のコンテナは、1 つの構成ぶんだけにする。自分のコンテナが、種類を問わず 1 つでも動いていたら断る (動いているのが重みの取得なら、その終わりを待つ)。終了した自分のコンテナが残っているときも断り、記録を回収してから停止のコマンドで消すよう促す (残したまま起こすと、名前の衝突になる)。ただし、選んだ構成と、名前、イメージのダイジェスト、構成の sha256 が 2 台とも一致する場合は、関門の前に「すでに動いている」として扱う
  - GPU の関門は、自分のコンテナの関門のあとに流すので、条件は「GPU を使っているプロセスが 1 つでもあれば、名前とメモリの量を示して断る」だけにする。GPU を使わない種類 (取得、イメージの中の読み取り) でも、同じ関門を流す
  - 使う待ち受けのポートは、別の一覧で持たず、構成の設定に付けた印から集める
  - 置き場所がなければ、配布を促して断る (結び付けは、元のディレクトリを自動では作らない)
  - 確認の種類 (縮小の確認) の構成では、重みの照合と空きの関門は、マニフェストのうち safetensors を除いたファイル (設定とトークナイザ) だけを、縮小の確認用の置き場所について見る
  - よそのものについて読むのは、GPU を使っているプロセスの名前とメモリの量だけ。ラベルのないコンテナに、どの操作も向けない
  - 了承を得る計画は、前に進むコマンドと、巻き戻すコマンド (その計画が起こす名前のコンテナの停止と削除だけ) の組として作り、全体を見せる。ほかの名前を、巻き戻しに入れられない
  - 読み取りの部品の試験は、1.6 で採った実物の出力を見本に使う
  - 了承: 計画と対象の機械を見せて、`yes` の入力を待つ。`--yes` のときは、見せてから通す。端末でなく `--yes` もなければ、断る
  - 完了の状態: GPU を使っているプロセスがあるときに、名前とメモリの量を示して断る。重みの取得が動いている間の起動と、終了した自分のコンテナが残っているときの起動が断られる。置き場所がないときに、配布を促して断る。空きが足りないときに、要る量と空いている量を示す。ダイジェストが一覧の 2 番目にあっても通る。縮小の確認の構成では、重みの本体がなくても、設定とトークナイザが照合済みなら通り、要る空きが数十 MiB として計算される。偽の実行役に記録された、コンテナを対象にする操作のすべてが、ラベルで絞った一覧から来た識別子か、了承済みの計画が自分で起こす名前だけを対象にしている。使うポートがふさがっているときに、ポートの番号を示して断る
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 3.2, 3.3, 3.5_
  - _Boundary: guards_
- [x] 2.4 (P) 記録の回収と、置き場所の決まりを作る
  - 自分のコンテナの記録 (時刻つきの全量)、通信の記録、起動の記録を、2 台から、git の管理の外の、日時とコマンドと構成の名前が付いた場所に写す
  - 記録の末尾だけを読む口を持つ (起動の失敗のときに使う)
  - 完了の状態: 偽の実行役で、2 台ぶんの記録が決まった場所にでき、ラベルのないコンテナの記録を読む呼び出しが 1 つも出ない
  - _Requirements: 1.9, 7.8, 10.5_

- [ ] 3. 取得と運転
- [x] 3.1 (P) イメージの取得、照合、ライセンスの表記の読み取りを作る
  - 関門 (入れるか、空き) → 了承 → 2 台でダイジェストでの取得 → 照合、の順に進める
  - イメージの中の、ライセンスの表記の候補のファイルを読む。読み取りの種類の構成を書いて、ほかの種類と同じく、名前とラベルを付けて切り離して起こし、終了を待ち、コンテナの出力を読んで表示してから消す。読むファイルの道筋は、構成の位置の引数として持ち、動かすプログラムは docker の設定で表す
  - 完了の状態: 偽の実行役で、了承しないと取得の呼び出しが出ない。取得のあとにダイジェストが合わなければ、食い違いを示して失敗する。ライセンスの表記の読み取りが、切り離して起こす呼び出しとして記録され、終了時に自動で消す指定を含まない

- [x] 3.2 (P) 重みのマニフェストを Mac で作る
  - Hub の公開の API から、固定した版のファイルの一覧、大きさ、sha256 を取る。LFS でない小さなファイルは、取得して sha256 を計算する。認証の情報を使わない
  - モデルカード (`README.md`) と `.gitattributes` は、取得も記載もしない
  - 完了の状態: 偽の API の応答から、名前の順のマニフェストができる。モデルカードを取得する要求が 1 つも出ないことを、試験で確かめる。同じ入力から、同じファイルができる
  - _Requirements: 3.4, 8.8, 11.3_
  - _Boundary: weights_
- [x] 3.3 重みの取得と、2 台での照合を作る
  - 関門 (空き) → 了承 → 2 台で並行に、取得の種類の構成から組み立てたコンテナで、固定した版を取得する。ホストに何も入れない。トークンを渡さない
  - 取得の構成も、ほかの種類と同じ形で書く (動かすプログラムは docker の設定、リポジトリの名前は位置の引数、設定の 1 つ 1 つに根拠)。名前とラベルを付けて、切り離して起こし、終わりは、コンテナの状態と終了コードで見る。ssh が途中で切れても取得は続き、もう一度打つと、動いている取得を見つけて待つ (二重に取得しない)。状態の確認と停止から、取得のコンテナが見える
  - 縮小の確認に使う、設定とトークナイザだけの取得と照合もできる (取得元は、縮小の確認の構成が指す重みの参照。マニフェストのうち、safetensors を除いたファイルを対象にする)
  - 照合: 2 台で sha256 を計算し、Mac の側でマニフェストと突き合わせ、結果を記録として残す。合わないファイルは、名前を並べて失敗にし、黙って取り直さない
  - 完了の状態: 偽の実行役で、1 行だけ違う sha256 の出力に対して、そのファイルの名前を示して失敗し、取り直しの呼び出しが出ない。取得のコンテナに渡る環境変数に、トークンがない
  - _Requirements: 2.5, 2.6, 3.4, 3.5_
  - _Boundary: weights_

## Implementation Notes

- 1.2: 検査 1〜4 (根拠の組み合わせ、イメージのダイジェストの形、版の 40 桁、`served_model_name`) は、型 (pydantic) の段で断る。入れ子の `Setting` が落ちると、その構成の `ConfigDef` の after 検証が走らないので、1.3 で「すべて並べて示す」を満たすには、設定を 1 つずつ検証して誤りを集める
- 1.2: `kind` ごとのノードの数 (serve / job / fetch は 2、probe / inspect は 1) は、型では断っていない。1.3 で検査する
- 1.2: 記録の回収 (2.4) の結果に専用の型はない。回収の結果は `Path`、末尾は `dict[NodeRole, str]` で表す。`LinkReport` は 1 台ぶん。netcheck の sanity、image、weights の結果の型は、凍結の対象の外 (4.4、3.1、3.2、3.3) で、要るときに足す
- 1.3: 検査 6 (置き換えの印) は、波かっこの組のうち、中身が空か `"` で始まるものを、JSON の値として文字のまま通す (縮小の確認の `--hf-overrides` のため。design の検査 6 の文言と probe の節の食い違いを、検査の目的を保って両立させた)。TOML では、JSON の値はリテラル文字列 (`'…'`) で書く。**2.1 の置き換えは、`str.format` ではなく、決まった 7 つの印の文字列の置換で行う** (JSON の波かっこを壊さない)
- 1.3: `--mount` の元は、`{remote_root}` そのものか、`{remote_root}/` で始まり、残りの道筋に `..` を含まないものだけ。plan (2.1) には元の道筋の検査がないので、config が唯一の歯止め。`--device` と `--cap-add` は完全一致 (`/dev/infiniband:rwm` は断る)
- 1.3: `schema_version` は configs.toml で必須、nodes.toml では書いてあれば確かめる。入れていない検査: `kind` ごとの weights の有無、nodes.toml の直結の 3 項目の「全部か全部なし」(検査 7 で `serve` と `job` のときに現れる)。pydantic の緩い型変換 (`"1800"` → 1800) は残っている
- 1.4: `remote` は、design より厳しい歯止めを 3 つ持つ (module の docstring の「意図した違い」)。(a) rsync の遠隔の道筋、`remote_root`、`ssh_host` は、使える文字を絞る (`[A-Za-z0-9._/-]`。この Mac の rsync は openrsync で `--protect-args` がない)。(b) `ip` は `link` / `addr` の読み取りの形、`ethtool` は `<if>` / `-i` / `-S` だけ (要件 2.7)。(c) `cat` は `remote_root`、`/sys/class/net/`、`/sys/class/infiniband/` の下だけ (要件 2.4、2.6)。4.3 がほかの読み取りの形を要るなら、`remote.py` の一覧を広げる変更を、1 つの作業として先に行う
- 1.4: ssh の `--` は宛先の前に置く (2026-09-21 に、読み取りのコマンドで、宛先の前と後のどちらも実機で通ることを確かめた)。`mutating=False` と申告されても、`docker run` / `stop` / `rm` / `pull` と `mkdir` は、了承の検査に掛かる。了承は `SshRunner.approve(plan)` で、関門のあとに 1 度だけ渡す
- 1.4: `FakeRunner` は、分類では Stub + Spy (Fake でも Mock でもない。名前は `bench` と design に合わせた)。検査は `remote.CallGuard` を実物と共有する。台本に合わない呼び出しは、既定で `AssertionError` (広く流す試験は `default=Reply()`)。ssh の失敗と時間切れは、`Reply(exit_code=255)` か `Reply(raises=RemoteError(...))` で書く (`subprocess.TimeoutExpired` を台本に書かない)。`Reply.writes` の「宛先の外に書かない」検査には、まだ試験がない
- 1.5: `fake_vllm.py` は、分類では Stub + Spy。5 つの道筋のどれでも、`set_X_fault` / `set_X_fault_sequence` に `Fault(status, body)` を渡して、200 以外の状態、応答しない (`status=None`)、壊れた本文を作れる (列が尽きたら最後を繰り返す)。`/metrics` の値は完全に台本任せで、`/v1/messages` の呼び出しと連動しない (「固まった」は、`set_metrics_sequence` で値を据え置いて作る)。`/v1/messages` の応答は、`set_messages_factory` で要求の本文に応じて選べる
- 1.5: 投機的デコードの指標の名前の接尾辞 (`_total`) は未確認。受け付けの判定は接頭辞 `vllm:spec_decode_` で見るので効かないが、8.2 で実物の `/metrics` を読んだときに確かめる
- 1.5: 実装担当の RED の記述 (実行時の失敗で `16 passed, 7 failed`) は、コミットした形の試験 (module の先頭で import) では再現せず、収集の誤りになる。レビュー担当が、分岐を壊す変異で試験が落ちることを確かめて補った。以後、RED の出力は、コミットする形の試験で再現できるものを採る
- 1.6: 見本は `serving/tests/fixtures/spark/{head,worker}/` (読み方と、置き換えた値は、そこの README.md)。空のファイルは、空の出力の見本 (自分のコンテナがない、GPU のプロセスがない)。**`ethtool <if>` は、root でなくても終了コード 0 だが、標準エラーに `netlink error: Operation not permitted` を出す** (4.3 は、これを誤りにしない)。つながっていないインターフェースは `Speed: Unknown!`。`ip -br link` は MTU を出さないので、4.3 が MTU を読む形を決めたら、見本を足す
- 1.6: 直結の側は、2 台とも、つながっているインターフェースが 2 つ (`enp1s0f0np0` = 192.168.100.x、`enP2p1s0f0np0` = 192.168.101.x。どちらも 200000Mb/s)。本数の判断と PLAN.md の訂正は 7.3。`[N/A]` の列の有無は、GPU のプロセスがないので未確認 (7.2 で採る)
