# Brief: vllm-baseline

PLAN.md の P1「上流の vLLM だけで出発点を作る」を、1 つの仕様として進めるための下調べの記録。
2026-09-21 の discovery の結果である。

## Problem

このリポジトリの開発者 (計測者) は、GLM-5.3-Flash を DGX Spark 2 台 (GB10、TP=2) で動かす推論サーバーを、
業務で使えるライセンスとクリーンルームの条件のもとで、自分たちの手で組み立てたい。P0 で測る道具 (`bench/`) は
できたが、測られる側 (自分たちで立てた推論サーバー) がまだ 1 つもない。上流の vLLM をパッチなしで使って
どこまで行けるのか、どこで止まるのかが、わかっていない。これがわからないと、P2 以降 (重みの選定、
投機的デコード、長い会話での安定性) で、何を自分たちで直す必要があるのかを決められない。

## Current State

- `bench/` (P0) は main に入っている。Anthropic 互換の `/v1/messages` に応答する対象サーバーなら、速さ、品質、
  長い会話でのツール呼び出しを、同じ手順で測れる。計測の前の確認は `scripts/spark-precheck.sh` (読み取りだけ)
- 2 台の Spark は空いている。計測者が別に起動していた構成 (コンテナ `exl3-tp2`) は、2026-09-21 に計測者の了承を得て
  止めた (コンテナは消していない。戻すなら `docker start exl3-tp2` を worker → head の順)。この構成の中身は、
  クリーンルームのため、設計にも実装にも使わない
- `scripts/` にあるのは、事前の確認のスクリプトだけ。起動、停止、配布の仕組みはない
- 公式の資料の調査 (2026-09-21、公式の文書と上流のソース・issue・PR だけを使った) でわかったこと:
  - 上流の vLLM は、PR #53906 (2026-09-03 に main にマージ) で GLM-5.3-Flash に対応した。リリース v0.29.0 には
    入っておらず、nightly か、Docker Hub の公式リポジトリのモデル別のプレビュー (`vllm/vllm-openai:glm53-flash-arm64-cu130`) が要る
  - **いちばんの懸念**: このモデルのアテンション (位置埋め込みの次元が 0 の sparse MLA) に対して、GB10 (sm_121) で
    選べるバックエンドは 2 つだけで、片方は sparse に非対応、もう片方は `pe_dim must be 64` で落ちる報告がある
    (issue #57578、未解決。修正の PR #53969 は Open)。一方で、ほぼ同じ構成で起動できている報告もある (issue #57087)。
    実機で試すまで、パッチなしで起動できるかはわからない
  - 起動できた場合の懸念: 同時に流すと日本語が文字化けする報告 (#57087、未修正)、GB10 2 台の TP=2 で 35〜55 分後に
    両方のノードが固まる報告 (#41725、未解決)、CUDA グラフでの NaN (#57156)、NVFP4 の MoE のカーネルの自動の選択 (#54666、#50934、#47365、#49079)
  - 約 4 ビットの重み (MIT だけ): 開発元の公式の 4 ビット版はない。第一の候補は `RedHatAI/GLM-5.3-Flash-NVFP4`
    (vLLM の公式の手引きが名指し、1 台あたり約 83 GiB、MTP を含む)。第二の候補は `canada-quant/GLM-5.3-Flash-W4A16-MTP`
    (INT4、GB10 を弾く判定が絡まないカーネル、1 台あたり約 89 GiB)。ライセンスの表記がないもの、非商用のものは使わない
  - 2 台での起動は、Ray を使わない公式の方法 (`--nnodes` / `--node-rank` / `--master-addr` / `--headless`、v0.11.1 以降) がある
  - GPUDirect RDMA は、DGX Spark では公式に非対応。NVIDIA の公式の手順は、NCCL の設定を `NCCL_SOCKET_IFNAME` しか入れていない
  - PLAN.md のハードウェアの記述と、公式の資料が食い違う点がある: 「直結リンク 2 本」は、同じ物理ポートの 2 つの顔で、
    ケーブルは 1 本かもしれない。MTU 9000 は、公式の資料に根拠がない
  - GLM-5.3-Flash のチャットテンプレートが読むのは `reasoning_effort` (low / high / 既定は max) と `clear_thinking` だけで、
    thinking を完全に切る手段はない

## Desired Outcome

- 上流の公式の vLLM イメージ (パッチなし) と、MIT の約 4 ビットの重みで、2 台の Spark に推論サーバーを起動できる。
  Mac から 1 つのコマンドで、配布、起動、状態の確認、停止ができる
- その対象サーバーに対して、`bench` の 5 つのまとまり (速さの 3 つ、品質、長い会話) を一通り流せて、要約ができている
- パッチなしでは起動できない、または計測を流し切れないとわかった場合は、どこで止まったか、何を試したか、
  直すのに要る最小の変更は何かが記録されていて、P1 の終わりの条件を改めるかどうかを、計測者が判断できる
- 「動かなかった箇所」の一覧ができている。これが、P2 以降で自分たちが直す場所の一覧になる
- `/v1/messages` の対応の状況 (ストリーミング、ツール呼び出し、長い会話、トークン数の内訳、`count_tokens`、thinking の渡し方) が、
  実機で確かめた事実として記録されている。足りないものがあれば、変換層を自分たちで書くか、上流に返すかの判断が
  `docs/decisions/` にある

## Approach

**切り分けながら、段階的に進める** (計測者が 2026-09-21 に選んだ)。安い段階で、いちばんの懸念に当たる。

1. **通信の確認**: `ip link` で直結のインターフェースの数を確かめる (ケーブルが 1 本か 2 本か)。NVIDIA の公式の手順に沿った
   素の設定で nccl-tests を流し、公式の実測 (約 190 Gbps) に対する到達の度合いを取る。NCCL のログで、RoCE の経路が
   使われていること、2 つのデバイスが束ねられているかを確かめる。vLLM の公式の事前の確認 (`torchrun` での `test.py`) を通す
2. **1 台だけでの起動の確認**: コンテキストを絞って 1 台で起動を試み、アテンションと MoE のバックエンドに何が選ばれるか、
   どこで落ちるかを記録する。モデルとカーネルの問題と、2 台の通信の問題を分けるため
3. **2 台で TP=2**: 第一の候補の重み (NVFP4) と、Ray を使わない方法で起動する。KV の大きさ、選ばれたバックエンド、
   NCCL の経路を記録する
4. **`bench` を一通り流す**: 速さ、品質、長い会話。日本語の同時の要求での文字化けと、2 時間の連続の負荷での固まりを、
   あわせて確かめる
5. **だめなら、順に代替を試す**: INT4 の重み → PP=2 → 明示の指定 (`--enforce-eager`、MoE のバックエンドの明示など)。
   それでも起動できなければ、必要な最小のパッチを特定して記録し、計測者に判断を仰ぐ (終わりの条件を
   「パッチなしで起動」から「必要な最小のパッチの特定」に改めるかどうか)

採らなかった案: いきなり 2 台の TP=2 を狙う (動かなかったときに、原因を切り分けにくい)。最初から未マージの PR を当てた
イメージを自分でビルドする (「上流だけでどこまで行けるかを知る」という P1 の趣旨に反する)。

## Scope

- **In**:
  - `scripts/` の、配布 (rsync)、起動、状態の確認、停止のスクリプト。Mac から ssh で動かす。head と worker の起動の順序を含む
  - 使う公式の vLLM イメージの選定と、ダイジェストでの固定。重みの取得と、2 台への配布と、同じであることの確かめ
  - 2 台での TP=2 の起動の構成 (コンテナの起動の引数、vLLM の引数、NCCL の設定)。根拠は、公式の資料か、自分たちの実測に辿れること
  - 通信の確認 (nccl-tests、NCCL のログ、vLLM の公式の事前の確認)
  - `bench/config/targets.toml` への、自分たちの対象サーバーの定義の追加と、`bench` を一通り流した結果の要約
  - `/v1/messages` の対応の状況の確認と、足りないときの判断の記録 (`docs/decisions/`)
  - 動かなかった箇所の一覧 (`docs/`)。`LICENSES.md` への、イメージ、重み、nccl-tests などの行の追加
  - PLAN.md のハードウェアの記述の、実測に基づく訂正
- **Out**:
  - 重みの形式どうしの本格的な比較と決定 (P2)。P1 は、起動できる 1 つを選ぶだけ
  - 投機的デコード (MTP) の調整 (P3)。P1 では、まず切ったままで起動し、入れるかどうかは起動できてから決める
  - 長い会話でツール呼び出しが崩れる原因の切り分け (P4)、通信と性能の詰め (P5)、自動起動と監視と連続稼働の試験 (P6)
  - vLLM へのパッチ、変換層の実装。P1 は、要るかどうかを判断して記録するところまで
  - `bench` 自体の変更。足りないものが見つかったら、`bench-harness` の側の変更として扱う

## Boundary Candidates

- **配布と運転** (`scripts/`): Mac → Spark の rsync、コンテナの起動と停止、状態の確認、ログの回収。対象サーバーの構成に依らない部分
- **対象サーバーの構成** (イメージ、重み、起動の引数、NCCL の設定): 根拠つきの設定のファイル。構成を替えても、配布と運転の側は変わらない
- **確かめの手順と記録** (通信、1 台での起動、2 台での起動、`bench`): 各段で何を見て、何を記録するか。動かなかった箇所の一覧
- **判断の記録** (`docs/decisions/`): イメージと重みの選定、`/v1/messages` の不足の扱い、終わりの条件を改めるかどうか

## Out of Boundary

- 計測の道具 (`bench/`) の中身。この仕様は、`bench` を使う側である
- 計測者が別に起動していた構成 (`exl3-tp2`) の中身。止める・戻すは、名前だけで行う
- Spark の OS、ドライバ、カーネル、ネットワークの恒久的な設定の変更。要るとわかったら、計測者に知らせて判断を仰ぐ
- 第三者のレシピ、ブログ、フォーラムにある起動のスクリプトや設定。開かない

## Upstream / Downstream

- **Upstream**: `bench-harness` (P0。`bench` のコマンド、`scripts/spark-precheck.sh`、対象サーバーに求める前提)。
  上流の vLLM の公式イメージと、Hugging Face の重み。NVIDIA の公式の 2 台の接続の手順と nccl-tests
- **Downstream**: P2 (重みの選定) は、この仕様の起動の仕組みと、動かなかった箇所の一覧を使う。P3 (投機的デコード)、
  P4 (長い会話での安定性)、P5 (通信の詰め)、P6 (運用) も、この仕様の `scripts/` と構成の上に積む

## Existing Spec Touchpoints

- **Extends**: なし (新しい仕様)
- **Adjacent**: `bench-harness`。`bench/config/targets.toml` に対象サーバーの定義を足すのと、`LICENSES.md` に行を足すのは、
  この仕様が行う。`bench/src/` は変えない。`scripts/spark-precheck.sh` は、GPU を使ってよいプロセスの名前の正規表現を
  引数で受けるので、そのまま使える見込み

## Constraints

- **ライセンス**: MIT、Apache-2.0、BSD 系だけ。NVIDIA の NGC のコンテナは、独自の EULA で、版も古いので使わない。
  非商用のドラフター、ライセンスの表記のない重みは使わない。採用した部品は `LICENSES.md` に書く
- **クリーンルーム**: 参照してよいのは、公式の文書、論文、モデルカード、上流の vLLM と NCCL のソースと issue と PR、自分たちの実測。
  vLLM プロジェクト自身の手引き (`recipes.vllm.ai`) と、NVIDIA 自身の DGX Spark の手順集 (`NVIDIA/dgx-spark-playbooks`、Apache-2.0) は、
  当事者の公式の文書として参照してよい (2026-09-21 に計測者に確認)。ただし、コマンドをそのまま写さず、事実だけを使う。
  設定の 1 つ 1 つに、根拠 (公式の資料の URL か、自分たちの実測) を添える
- **文脈の切り離し**: この discovery を行ったセッションは、`exl3-tp2` の起動の構成を 1 度見てしまった。起動の構成、NCCL の設定、
  vLLM の引数の設計と実装は、その文脈を持たない新しいサブエージェントか、新しいセッションが、公式の資料だけから行う。
  レビューでは、根拠に辿れない設定を差し戻す
- **どこで何をするか**: リポジトリの正本は Mac。Spark の上でファイルを編集しない。配布は rsync、実行は ssh。Spark に GitHub の認証の情報を置かない
- **Spark の状態を変える操作** (コンテナの起動と停止、イメージの取得、重みの配布、パッケージの導入) は、実行の前に計測者に確認を取る。
  計測のときは、対象以外のモデルが動いていない状態にする (`scripts/spark-precheck.sh`)
- **資源**: 1 台あたりのユニファイドメモリは 121.7 GiB。重みは 1 台あたり 83〜89 GiB で、KV に回せるのは 10〜15 GiB ほどの見込み。
  ディスクの空きは 2 台とも 2.5 TB 以上。重みの取得は 1 つにつき 160〜180 GiB
- **委譲の方針** (CLAUDE.md): 要件、設計、レビュー、統合の判断はメインのセッション。範囲の明確な実装はサブエージェント

## 訂正の注記 (2026-09-22、research.md による)

この discovery (2026-09-21) のあとの調査 (`research.md`) で、次の 3 点の訂正が要ることがわかった。本文は書き換えず、ここに注記として残す。

- **(a) 重みの大きさ**: 「Current State」と「Constraints」に書いた「`RedHatAI/GLM-5.3-Flash-NVFP4` … 1 台あたり約 83 GiB」は誤りである。実測 (Hugging Face Hub API) では合計 184.3 GiB で、TP=2 では **1 台あたり約 92 GiB** になる (埋め込みと lm_head が両ノードに複製されるので、正確にはこれより少し多い)。根拠は research.md §b-2
- **(b) メモリで効くのは KV よりも KDA の状態**: 「Constraints」の「KV に回せるのは 10〜15 GiB ほどの見込み」は、数字としては妥当である。ただし、実際にメモリを圧迫するのは KV キャッシュよりも **KDA (線形アテンション) の状態**である。45 層のうち 34 層が線形アテンションで、その状態は文脈長ではなく**同時実行数に比例**する (1 本あたり約 70 MiB/ノード)。既定のままでは `--max-num-seqs` が大きな値になり、数十 GiB を失う。**`--max-num-seqs` を明示的に小さく設定する** (Decision 6。根拠は research.md §d-6〜§d-8)
- **(c) 第二の候補のモデルカードは開かない**: 「Constraints」の「クリーンルーム」で「モデルカード」を参照してよい資料に挙げているが、第二の候補 (`canada-quant/GLM-5.3-Flash-W4A16-MTP`) のモデルカードは **DGX Spark 2 台の起動レシピそのもの**であり、クリーンルームの条件 (要件 11.3、8.8) では開かない (Decision 11。根拠は research.md §b-7)
